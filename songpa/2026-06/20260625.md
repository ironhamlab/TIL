* 단원명 : Spring Boot 프로젝트
* 학습 주제 : 마이크로서비스에서 데이터를 안전하게 건너가게 만드는 5가지 장치

---


#### [학습 내용]

Trading Service 인프라를 보면서 BFF, gRPC, 멱등성, Outbox 패턴, Kafka 다섯 개념을 정리했다. 처음엔 각자 다른 기술처럼 보였는데, 결국 다 같은 질문에 대한 답이었다.

> **"여러 시스템에 걸친 작업을 어떻게 안전하고 끊기지 않게 연결할까?"**

이 질문은 주문/체결뿐 아니라 배치, 실시간 시세, 알림 어디에도 똑같이 적용된다. 다만 두 가지 변수(속도, 유실 허용 여부)에 따라 쓰는 도구가 달라질 뿐이다.

```
실시간 시세  → 초당 수천 건, 유실돼도 괜찮음 → Redis Pub/Sub
주문/체결    → 요청당 1번, 유실되면 안 됨   → gRPC + Outbox/Kafka
알림        → 이벤트당 1번, 유실되면 안 됨   → Kafka
배치        → 하루 1번, 정해진 시간          → 배치 + 재시도
```

---

### 1. BFF — 여러 서비스를 한 곳에서 모아주는 대리인

화면 하나(예: 계좌 대시보드)가 주문, 포트폴리오, 랭킹 세 서비스의 데이터를 동시에 필요로 할 때, 클라이언트가 직접 세 번 호출하지 않게 중간에서 모아주는 계층.

**BFF가 하는 일**
- 여러 서비스를 병렬로 호출해서 응답을 하나로 조합 (DB 조인이 아니라 메모리상에서 짝짓기)
- REST(클라이언트용) ↔ gRPC(내부용) 통역
- 인증 토큰을 한 번 검증해서 메타데이터로 전달
- 멱등성 키를 그대로 전달 (직접 만들지 않음)

**BFF가 절대 안 하는 일**
- 다른 서비스 DB 직접 조회
- 잔고 차감, 주문 체결 같은 정합성 있는 계산
- 여러 서비스를 묶는 분산 트랜잭션
- 멱등성 키 생성

> 핵심: 진짜 계산은 항상 도메인을 소유한 서비스가 하고, BFF는 결과를 모아 배치만 한다.

---

### 2. gRPC — 내부 서비스끼리 빠르게 대화하는 방법

RPC(원격 함수 호출)를 HTTP/2 + Protobuf + `.proto`로 구현한 프레임워크.

**왜 REST보다 빠른가**
| 기능 | 누구 덕분인가 |
|---|---|
| connection 하나로 여러 요청 동시 처리 (멀티플렉싱) | HTTP/2 |
| header 압축 (HPACK) | HTTP/2 |
| 이진 직렬화로 body 크기/파싱 비용 감소 | Protobuf |
| 런타임 에러를 컴파일 타임으로 앞당김 | .proto |

**왜 굳이 씀**: 클라이언트↔BFF 구간은 보편적 접근성이 중요해서 REST. BFF↔내부 서비스 구간은 우리끼리만 통신하니 보편성 필요 없고, 대신 돈 다루는 타입 안정성 + 병렬 호출 효율이 중요해서 gRPC.

**타입이 세 번 변신한다**
```
PlaceOrderRequest (proto, 자동생성) 
  → PlaceOrderCommand (도메인, 직접작성) 
  → OrderEntity (DB, 직접작성)
```
도메인 계층이 proto 타입을 직접 알면 gRPC에 종속되어버리니까 일부러 나눠둔다.

---

### 3. 멱등성 — 같은 요청 두 번 와도 한 번만 처리되게

**문제**: 네트워크는 "응답을 못 받은 것"과 "처리가 안 된 것"을 구분 못 해준다. 그래서 재시도하면 중복 처리될 위험이 있다.

**클라이언트→서버 멱등성** (UUID 방식)
- 클라이언트가 UUID 생성 → 서버가 DB에서 "처리한 적 있나" 확인
- 같은 UUID로 다른 내용이 오는 위조를 막기 위해 SHA-256 해시 비교 필요
- 동시 요청은 DB 복합키 unique 제약으로 방어

**Kafka→Consumer 멱등성** (event_id 방식)
- 서버가 직접 event_id 발급 → 위조 불가능하므로 해시 비교 불필요
- ID 비교만으로 충분 ("멱등한 컨슈머" 패턴)

> 둘 다 "같은 키로 이미 처리했는지 DB 확인 + 처리와 기록을 한 트랜잭션으로" 라는 원리는 같다. 키를 누가 만드느냐(클라이언트 vs 서버)만 다르다.

---

### 4. Outbox 패턴 — DB 저장과 메시지 발행을 안전하게 묶기

**문제**: DB 저장과 Kafka 전송은 별개 시스템이라 하나의 트랜잭션으로 묶을 수 없다. 둘 중 하나만 성공하면 데이터 불일치가 생긴다.

**해결**: Kafka로 직접 안 보내고, 같은 DB 안에 `outbox_events` 테이블을 두고 "보낼 목록"만 기록. 도메인 변경과 같은 트랜잭션으로 묶인다. 실제 발행은 별도 프로그램이 폴링해서 처리.

```
[트랜잭션] 주문 저장 + outbox_events 기록  ← 원자적
       ↓
[별도 프로그램] 미발행 이벤트 조회 → Kafka 전송 → published_at 기록
```

구조상 **최소 한 번(at-least-once) 전달**이 보장되고, 두 번 갈 수도 있다는 게 특징. 그래서 Consumer 쪽 멱등성 처리가 필수.

---

### 5. Kafka — 동기 호출의 "상대가 살아있어야 한다"는 제약을 없앰

gRPC/REST 직접 호출은 호출받는 서비스가 그 순간 살아있어야 한다. 서비스가 늘어날수록 trading-service가 모든 서비스의 생사에 종속된다.

**해결**: 토픽에 메시지만 올려두면 끝. 누가 읽는지 신경 안 씀 (비동기, 느슨한 결합).

- **토픽**: 메시지 게시판
- **프로듀서**: Outbox 발행 프로그램
- **컨슈머**: portfolio-service, notification-service 등
- **파티션**: 같은 주문 ID는 항상 같은 파티션 → 순서 보장 (`OrderPlaced`가 `OrderCancelled`보다 먼저 도착하도록)

메시지는 컨슈머가 안 읽어도 사라지지 않고 보관된다.

### 전체 흐름 한 장으로

```
웹앱
  │ REST + 멱등성 키(UUID, 여기서 생성)
  ▼
BFF (병렬호출/조합, REST↔gRPC 통역, 인증/키 전달)
  │ gRPC + 같은 멱등성 키 그대로 전달
  ▼
[멱등성 1차 체크: 해시 비교 + DB PK]
  ▼
trading-service
  도메인 로직 처리
  └→ Outbox 테이블에 기록 (같은 트랜잭션)
  ▼
별도 발행 프로그램이 폴링
  ▼
Kafka (order-events 토픽, 주문ID로 파티션 결정)
  ▼
[멱등성 2차 체크: event_id만 비교, 해시 불필요]
  ▼
Consumer (portfolio-service, notification-service...)
```

### 오늘의 한 줄 정리

> 데이터가 한 시스템에서 다른 시스템으로 건너가는 모든 지점마다, "정확히 한 번만, 늦지 않게 전달됐는가"를 보장하는 장치가 필요하다. 그 모양은 상황(요청-응답 / 사건 전파 / 끊김없는 흐름 / 정기 배치)에 따라 멱등성 키, Outbox+Kafka, Redis Pub/Sub, 배치 재시도로 각각 다르게 구현될 뿐 본질은 같다.

### 헷갈렸던 부분 (나를 위한 메모)

- **event_id vs aggregate_id(주문ID)**: event_id는 "이 이벤트 자체"의 고유번호(중복방지용), aggregate_id는 "어떤 주문에 대한 것인지"(순서보장/파티션용). `OrderPlaced`와 `OrderCancelled`는 event_id는 다르지만 같은 주문이면 aggregate_id는 같다.
- **인터셉터 vs Executor**: 인터셉터는 형식 검증만(가벼운 일, 모든 요청에 적용), Executor가 실제 DB 조회/판단(무거운 일, 쓰기 API에만 적용). 우체국 접수창구 vs 분류 담당자 비유로 이해.
- **왜 추상클래스가 아니라 인터페이스가 아닌가**: 구현 안 한 RPC가 있어도 빌드가 깨지지 않게 하려고 (`UNIMPLEMENTED` 기본 동작 깔아둠).

#### [느낀 내용]

- 다섯 개의 키워드(BFF, gRPC, 멱등성, Outbox, Kafka)를 따로 외울 때는 그냥 "마이크로서비스에서 쓰는 기술 목록"처럼 느껴졌는데, "데이터가 한 곳에서 다른 곳으로 안전하게 건너가야 한다"는 하나의 질문으로 묶어서 보니까 왜 이 조합이 필요한지가 이해됐다. 결국 다 "동기 호출의 한계를 어디서, 어떻게 끊어줄 것인가"에 대한 답이라는 게 핵심이었다.
- 멱등성을 클라이언트→서버와 Kafka→Consumer 두 가지로 나눠서 본 게 가장 인상적이었다. 같은 "멱등성"이라는 단어를 쓰지만 "키를 누가 만드느냐"에 따라 해시 비교가 필요한지 아닌지가 갈린다는 걸 명확히 짚어주니, 왜 어떤 코드는 해시까지 검사하고 어떤 코드는 ID만 비교하는지 헷갈렸던 부분이 풀렸다.
- Outbox 패턴이 "DB와 Kafka를 하나의 트랜잭션으로 묶을 수 없다"는 아주 단순한 제약에서 시작된다는 걸 보고, 분산 시스템에서의 많은 패턴들이 결국 "할 수 없는 것"을 인정하고 그 주변에 안전장치를 두는 방식으로 설계된다는 느낌을 받았다. 완벽한 원자성을 포기하는 대신 at-least-once + 멱등한 컨슈머로 보완하는 트레이드오프가 인상적이었다.
- BFF가 "절대 하지 않는 일" 목록을 보면서, 좋은 아키텍처 경계는 "무엇을 하는가"보다 "무엇을 하지 않는가"로 더 명확하게 정의된다는 생각이 들었다. 인프라/DevOps 쪽에서도 똑같이 적용되는 원칙 같다
- 각 계층이 자기 책임만 지켜야 전체 시스템을 추론하기 쉬워진다.
- gRPC가 단순히 "REST보다 빠른 기술"이 아니라 HTTP/2(전송), Protobuf(직렬화), .proto(계약) 세 가지가 합쳐진 결과라는 걸 표로 분리해서 보니, 평소 "gRPC가 빠르다"는 말을 들었을 때 정확히 어느 부분 때문에 빠른 건지 설명을 못 했던 게 채워졌다.

#### [활용 방안]

- 향후 프로젝트에서 외부 API 호출(금융감독원 API, LLM API 등)을 처리할 때, 단순 호출-응답이 아니라 "이 호출이 실패와 타임아웃을 구분 못 한다"는 전제를 깔고 멱등성 키를 설계에 넣는 습관을 들인다.
- k3s 기반 인프라를 구성할 때 서비스 간 통신을 무조건 동기 호출로 엮지 않고, "이 데이터가 유실되면 치명적인가"를 먼저 따져서 Kafka/메시지 큐가 필요한 구간과 단순 REST/gRPC로 충분한 구간을 구분하는 기준으로 삼는다.
- 포트폴리오 정리 시 다른 프로젝트의 아키텍처 결정을 설명할 때, 단순히 "이 기술을 썼다"가 아니라 오늘처럼 "문제 → 원인 → 해결"의 구조로 서술하면 면접에서 설계 의도를 더 설득력 있게 전달할 수 있을 것 같다.
- 다음에 비슷한 개념을 정리할 때, 오늘처럼 "원래 뜻 → 문제 → 원인 → 해결" 템플릿을 따라가면 새로운 기술을 배울 때도 표면적인 사용법이 아니라 "왜 필요한가"부터 이해하는 습관을 들일 수 있을 것 같다. 다음 학습 주제(FastAPI, RAG Architecture)에도 같은 틀을 적용해볼 예정.
