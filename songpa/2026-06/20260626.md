* 단원명 : Spring Boot 프로젝트
* 학습 주제 : MSA 도메인 패키지 리팩토링 & 응답 데이터 암호화 개념 서칭

---

#### [학습 내용]

**1. 도메인 패키지 구조 리팩토링 (`feat/trading-2-domain-package-restructure`)**
- 기존 레이어 기반(controller/service/...) 구조를 `account/`, `order/`, `reservation/`, `support/` 도메인 기반 구조로 전환
- `TradingDomainService` → `AccountService`/`DefaultAccountService`, `OrderService`/`DefaultOrderService`로 분리 (컨벤션상 `Impl` 대신 `Default` 사용)
- `TradingGrpcService`도 동일하게 `AccountGrpcService` / `OrderGrpcService`로 분리, proto 파일도 단일 `TradingService` → `AccountService`/`OrderService`/`ReservationService`로 분리 (breaking change로 확정)
- `IdempotencyExecutor`, `OutboxWriter`를 `IdempotencyOperations<ID, REC>`, `OutboxOperations<REC>` 인터페이스를 받도록 리팩토링 → 도메인별 인스턴스 안 만들고 어댑터만 주입하는 방식으로 변경
- Flyway 마이그레이션으로 `account`/`order_svc` 스키마와 도메인별 `idempotency_records`/`outbox_events` 테이블 분리 생성

**2. `bootRun` 검증 중 발생한 문제 3가지 해결**
- 동일한 이름의 Repository 인터페이스가 도메인마다 존재해 Spring 빈 이름 충돌 → 도메인 prefix로 해결 (`AccountOutboxEventRepository`)
- 동일한 이름의 `@Entity` 클래스 충돌 → `@Entity(name = "AccountIdempotencyRecord")`로 해결
- Spring Boot 4.1.0에서 Flyway 자동 설정이 별도 모듈로 분리됨 → `spring-boot-flyway` 런타임 의존성 추가로 해결
- Jackson 2.x/3.x 충돌(`ObjectMapper` 주입 실패) → 명시적 2.x 의존성 제거 + `tools.jackson.*` 패키지로 import 변경

**3. `response_payload` 암호화 — 개념/자료 서칭 (구현 전 단계)**
- `IdempotencyRecord.response_payload`가 횡단 관심사(AOP)에 해당하는 요인임을 발견 → 팀장에게 보고 후 처리 진행 승인받음
- `AttributeConverter`는 메서드 호출이 아니라 **DB 읽기/쓰기 시점**을 가로채는 메커니즘이라는 점에서 AOP(`@Aspect`, gRPC `ServerInterceptor`)와 구분됨을 학습
- AES-256-GCM 암호화 방식, IV prepend 방식, `@Value`를 통한 키 주입 방식 등 구현에 필요한 개념과 자료 서칭 완료. 실제 `EncryptedPayloadConverter` 구현은 다음 단계로 진행 예정
- `request_hash`는 단방향 해시(중복 비교용)라 암호화 대상이 아니며, 암호화는 `response_payload`에만 적용해야 한다는 점도 함께 정리

**4. `claude.md` 작성 및 Git 컨벤션 정리**
- AI 코딩 어시스턴트용 컨텍스트 문서(`claude.md`) 작성: 패키지 구조, 하드 룰(낙관적 락 미사용, soft delete 금지, append-only 엔티티 등) 정리
- GitHub Issue 템플릿 5종 확정: `proposal`, `bug`, `etc`, `notice`(신규), `task`(신규, 최소 필드)
- `chore/` 브랜치 타입 신설(main에서 직접 분기), `common/dev` 브랜치 추가

#### [느낀 내용]

* 한 가지 기능 추가보다는 구조를 다시 세우고, 개념을 학습하는 날이었다.
* 패키지를 도메인 기준으로 쪼개는 작업이 생각보다 복잡했지만, 추후 내 도메인을 더 작은 단위의 서비스로 쪼개는 작업도 쉬워지고, 도메인 분리도 더 잘 될 것 같아서 꼭 필요한 작업이었다.
* 쪼개는 과정에서 Spring Bean 충돌, Entity 이름 충돌, Flyway/Jackson 버전 문제가 한꺼번에 터져서, 구조를 바꿀 때는 "숨어있던 암묵적 가정"들을 구체화하고 명시하는 방식으로 작업해야 하는 경우가 많을 것 같다고 느꼈다.
* `response_payload` 암호화 위치를 찾으면서 AOP(`@Aspect`, `ServerInterceptor`)와 `AttributeConverter`를 계속 비교하게 됐는데, 둘 다 "비즈니스 로직을 건드리지 않고 부가 기능을 끼워 넣는다"는 목적은 같지만 가로채는 지점이 다르다는 걸 명확히 구분하고 나서야 어디에 암호화를 적용해야 하는지가 보였다.
* 그동안은 AOP를 하나의 기술(예: `@Aspect`)로만 알고 있었는데, 이번에 정리하면서 "AOP는 횡단 관심사 분리라는 목표이고, `@Aspect`/`ServerInterceptor`/`AttributeConverter`는 그 목표를 구현하는 서로 다른 메커니즘"이라는 걸 깨달았다. 개념과 구현 수단을 분리해서 보는 시각이 생긴 느낌이다.


</br>

#### [활용 방안]

- 패키지 리팩토링 중 만난 Bean/Entity 이름 충돌, Flyway/Jackson 버전 이슈는 트러블슈팅 노트로 따로 정리해서 팀 공유 — 다른 도메인 담당자도 같은 구조 전환 시 동일 문제를 겪을 가능성이 높음
- `AttributeConverter` vs AOP(`@Aspect`/`ServerInterceptor`) 구분 기준("무엇을 가로채는가")은 추후 다른 횡단 관심사(로깅, 감사 등) 적용 위치를 정할 때도 재사용
- `response_payload` 암호화는 서칭 단계이므로, 다음 작업 시 `EncryptedPayloadConverter` 실제 구현 → 기존 평문 데이터 마이그레이션 전략까지 이어서 진행
- `claude.md`/Issue 템플릿은 한 번 정리해두면 팀원 온보딩 시 반복 설명이 줄어드는 효과 → 신규 합류자나 다른 도메인 담당자에게도 적용 가능
