#### [학습 내용]

**1. `EncryptedPayloadConverter` 라인별 재학습**
- Hibernate가 `convertToDatabaseColumn()` / `convertToEntityAttribute()`를 자동으로 호출한다는 점, 개발자가 직접 호출하지 않는다는 점을 코드 흐름으로 다시 확인
- IV(초기화 벡터)가 매번 달라야 같은 평문도 다른 암호문이 나오는 이유를 실제 바이트값 예시로 검증
- `static volatile SecretKeySpec` 패턴이 필요했던 이유: `common` 모듈이 컴포넌트 스캔 범위 밖이라 Spring 생성자 주입이 불가능하고, Hibernate가 Converter를 기본 생성자로 직접 인스턴스화하기 때문
- `volatile`이 멀티스레드 환경에서 하는 역할을 스레드 타임라인 예시로 정리

**2. 암호화 구현 1차 완성 & Gradle 의존성 문제 해결**
- `IdempotencyRecord.responsePayload`가 암호화 대상이고, `requestHash`는 대상이 아님을 재확인 — AOP(`@Aspect`/`ServerInterceptor`) 대신 `AttributeConverter`를 쓰는 이유(메서드 호출이 아니라 DB 읽기/쓰기 시점을 가로채기 때문)도 다시 정리
- `common` 모듈 Gradle 빌드 이슈: `jakarta.persistence-api:3.2.0`, `spring-context:7.0.8`을 `compileOnly`/`testCompileOnly`로 추가, `junit-bom:6.0.3` 적용 — 버전은 추측하지 않고 `./gradlew :services:account-service:dependencies`로 직접 확인
- Qodo 자동 코드 리뷰로 `@Component`가 컴포넌트 스캔 밖 클래스에는 동작하지 않는다는 버그를 발견 → `@Component`/`@Value` 제거하고 정적 홀더 패턴(`initKey(String base64Key)`)으로 전환, 이후 `spring-context` 의존성도 제거
- 라운드트립, IV 랜덤성, GCM 변조 탐지, 키 길이 검증 등 9개 단위 테스트 작성

**3. Reservation ↔ Order 비동기 연동 설계 (6가지 주문 조합 전체 매핑)**
- 즉시 시장가/지정가, 예약+전일종가, 예약+당일종가, 예약+시가+시장가는 단일 도메인 내에서 처리되지만, **예약+시가+지정가**만 Reservation→Order 두 도메인을 가로지름을 확인
- 동기 gRPC(B안), 직접 batch INSERT(A안), 비동기 Kafka 이벤트(C안) 세 가지를 비교 → 기존 Outbox/Idempotency 인프라를 재사용하면서 도메인 독립성을 지킬 수 있는 C안 채택 (단기 구현 속도보다 기술 부채 방지를 우선)
- `ReservationDue` → `ReservationConverted` 이벤트 체인 설계, 중간 상태로 `CONVERTING` 도입, 멱등성 키 패턴은 `reservation-due:{reservationId}`
- `OrderPlaced`를 재사용하지 않고 `ReservationConverted`를 별도로 둔 이유: 토픽 구독 시 불필요한 필터링을 피하기 위함

#### [느낀 내용]

* Qodo 리뷰를 통해 `@Component`가 컴포넌트 스캔 범위 밖에서는 동작하지 않는다는 걸 새롭게 알게 됐다. Hibernate가 Converter를 기본 생성자로 직접 인스턴스화한다는 것도 같이 알게 되면서, Spring의 DI가 "항상 보장되는 것"이 아니라 컴포넌트 스캔이라는 전제 조건 위에서만 동작한다는 걸 구체적인 실패 사례로 처음 체감했다.
* 6가지 주문 조합을 전부 매핑해보니 도메인 경계를 넘는 케이스가 "예약+시가+지정가" 단 1개뿐이었다. 처음엔 복잡해 보였는데 막상 전체를 그려보고 나니 예외 케이스가 생각보다 작다는 걸 확인할 수 있어서, 설계 전에 전체 매트릭스를 먼저 그려보는 게 범위를 줄이는 데 도움이 된다는 걸 다시 느꼈다.

#### [활용 방안]

* `static volatile` + `initKey()` 정적 홀더 패턴은 "Spring 빈이 아닌데 외부 설정값이 필요한 클래스"라는 조건이 또 나오면(예: 다른 `common` 유틸 클래스) 동일하게 재사용
* `common` 모듈처럼 컴포넌트 스캔 범위 밖에 있는 클래스를 작성할 때는 `@Component`/`@Value`를 쓰기 전에 "이게 Spring이 관리하는 객체인가, 프레임워크(Hibernate 등)가 직접 만드는 객체인가"부터 먼저 확인하는 걸 체크리스트로 삼기
* `ReservationDue` → `ReservationConverted` 같은 "전용 이벤트 분리" 패턴(공용 이벤트 재사용 대신)은 추후 다른 cross-domain 비동기 연동이 필요할 때 기본 설계 옵션으로 우선 고려
* 6가지 조합 전체 매핑 → 경계를 넘는 케이스만 골라내는 접근은, 다음에 Reservation 도메인 본격 구현 들어갈 때 테스트 케이스 설계 기준으로도 그대로 활용
* Flyway 마이그레이션 4개 분리 패턴(`스키마 생성` / `레거시 정리` / `도메인별 테이블`)을 정리해서, 다른 도메인 담당자가 비슷한 스키마 정리 작업할 때 참고하도록 공유
