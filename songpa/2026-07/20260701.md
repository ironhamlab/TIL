#### [학습 내용]

**1. Reservation 도메인 버그 수정 및 마이그레이션 (`V20260701_001`)**
- Qodo 코드 리뷰로 발견된 버그 4가지 수정:
  - CHECK 제약조건이 소문자 enum 값 기준으로 작성돼 있었으나 DB에는 대문자로 저장되는 불일치 → 대문자로 정정
  - enum 값 이름 변경(`CLOSE→TODAY_CLOSE`, `EXT_CLOSE→AFTER_HOURS_CLOSE`) 이후 CHECK 제약조건에 이전 값이 그대로 남아 있던 문제 → 변경된 이름으로 정정
  - 동일 예약 중복 방지를 위한 partial unique index 누락 → 추가
  - gRPC 서비스 레이어에서 `UUID.fromString()` 호출 시 잘못된 값이 들어올 때 `DateTimeParseException`이 처리되지 않던 문제 → `IllegalArgumentException` catch 블록 추가

**2. `ReservationBatchService` / `DefaultReservationBatchService` 구현**
- OPEN+LIMIT 예약에 대해 배치 서비스가 gRPC로 호출하면 `ReservationDue` 이벤트를 Outbox에 발행하는 흐름 구현
- `MarkReservationConverted` RPC 구현: 배치가 주문 전환 완료를 알리면 예약 상태를 `CONVERTED`로 변경
- OPEN+MARKET, TODAY_CLOSE, PREV_CLOSE 배치 처리는 Market 도메인 Kafka 스키마 확정 전까지 보류

**3. Spring Boot + Spring MVC vs Spring Boot + Spring WebFlux (팀 회의 발표 내용 학습)**
- Spring Boot는 실행/설정 프레임워크이고, Spring MVC / Spring WebFlux는 그 위에서 선택하는 웹 스택 — 두 비교 구도는 `Spring Boot + MVC` vs `Spring Boot + WebFlux`가 정확한 표현
- **Spring MVC**: Servlet 기반, 요청 1개당 스레드 1개, DB 응답을 기다리는 동안 해당 스레드는 블로킹 상태. 이해하기 쉽고 JPA와 잘 맞아 일반 CRUD 서비스에 적합
- **Spring WebFlux**: Reactive Streams 기반, 논블로킹. I/O 대기 중 스레드를 점유하지 않고 다른 요청 처리 → 적은 스레드로 높은 동시성 처리 가능. 반환 타입으로 `Mono<T>`(0~1개), `Flux<T>`(0~N개) 사용
- **Event Loop**: 소수 스레드가 여러 I/O 이벤트를 계속 확인하며 처리. 이 스레드 안에서 JPA 같은 블로킹 호출을 하면 WebFlux의 장점이 사라짐 → DB 접근도 R2DBC 같은 reactive driver와 함께 써야 의미 있음
- **back pressure**: 소비자가 생산자에게 처리 가능한 양을 알려 과부하를 방지하는 Reactive Streams의 핵심 메커니즘. 대량 스트리밍, SSE, 실시간 이벤트 처리에서 중요
- **WebFlux가 유리한 경우**: 외부 API 호출이 많거나 I/O 대기 시간이 긴 서비스, SSE/WebSocket/streaming 응답, 전체 I/O 체인을 non-blocking으로 구성할 수 있는 환경
- **WebFlux가 불리한 경우**: JPA 기반 서비스, 단순 CRUD, 팀이 reactive programming에 익숙하지 않은 경우 — 특히 WebFlux 컨트롤러 안에서 JPA를 그대로 호출하면 겉만 reactive이고 실제로는 블로킹이 되는 구조
- 의존성 선택: `spring-boot-starter-web`(MVC + Tomcat) vs `spring-boot-starter-webflux`(WebFlux + Netty) — 둘을 동시에 넣으면 MVC 쪽으로 구성되므로 하나만 선택해야 함

**4. WebSocket (팀 회의 발표 내용 학습)**
- HTTP는 클라이언트가 요청을 보내야만 서버가 응답할 수 있는 단방향 구조. WebSocket은 최초 HTTP Upgrade 핸드셰이크 이후 **양방향 지속 연결**을 유지
- 한 번 연결되면 클라이언트와 서버가 각자 먼저 데이터를 보낼 수 있음 → 실시간 시세 스트리밍, 채팅, 게임 등에 사용
- Candle 프로젝트에서는 BFF가 Market 서비스로부터 Redis Pub/Sub으로 시세 데이터를 받아 WebSocket으로 브라우저에 전달하는 구조 — trading-service는 이 흐름에 관여하지 않음

</br>

#### [느낀 내용]

* Qodo가 잡아준 버그 4개가 전부 "놓치기 쉬운 것들"이었다. 자동 리뷰 도구가 이런 케이스를 잡아주는 게 실질적으로 얼마나 중요한지 다시 체감했다.
* Spring MVC vs WebFlux는 팀원이 발표한 내용을 들을 때 반환 타입이 `Mono`/`Flux`로 바뀐다는 건 이해했는데, 정작 "왜 그게 의미 있는가"는 Event Loop와 블로킹 문제를 이해하고 나서야 연결됐다.
* WebSocket이 Candle 시스템에서 어느 위치에 있는지 오늘 확실히 정리됐다 — Market 서비스 → Redis Pub/Sub → BFF → WebSocket → 브라우저로 이어지는 흐름이고, trading-service는 그 경로에 없다는 것. 기술 개념을 배울 때 "우리 시스템에서 어디에 있나"와 연결해서 이해하니 훨씬 오래 기억에 남는 것 같다.

</br>

#### [활용 방안]

* Flyway 마이그레이션 작성 시 CHECK 제약조건 값이 실제 DB 저장 포맷(대소문자)과 일치하는지, enum 이름 변경 이후 기존 제약조건도 함께 업데이트했는지를 작성 완료 후 체크리스트로 반드시 확인
* WebFlux/reactive 기술 스택을 도입할 가능성이 있다면 "JPA를 그대로 유지할 수 있는가"를 생각해보고 채택하기 — non-blocking 효과를 내려면 DB 접근 레이어까지 포함해 전체 I/O 체인이 reactive해야 함
* `Mono`/`Flux`의 `map`(값 변환)과 `flatMap`(비동기 작업 연결) 구분은 추후 WebClient로 외부 API 조합 호출을 구현할 때 직접 적용
* WebSocket과 SSE의 차이(양방향 지속 연결 vs 서버→클라이언트 단방향 스트림)를 기억해두고, 추후 실시간 알림 기능 설계 시 요구사항에 맞는 방식 선택 기준으로 활용
