* 단원명 : Spring Boot 프로젝트
* 학습 주제 : OPEN+MARKET 배치 & 지정가 체결 완성, 1차 리뷰 준비

---

#### [학습 내용]

**1. OPEN+MARKET 배치 체결 구현 (#109)**
- `MarketPriceConsumer`: Kafka에서 Market 서비스의 시세 이벤트를 수신해 `CachedMarketPriceProvider`의 캐시를 업데이트하는 컨슈머 구현. `Clock` 주입으로 테스트 가능성 확보, poison pill 핸들링 추가
- `MarketPriceEvent`: Market 서비스로부터 수신하는 Kafka 이벤트 레코드 정의
- `processOpenMarketReservations`: 시가+시장가 예약에 대해 배치 체결 처리. 현재가는 `CachedMarketPriceProvider`에서 조회

**2. EXE-002 지정가 조건 체결 구현 (Order 도메인)**
- `OrderLimitFillExecutor`: self-invocation 방지를 위해 `DefaultOrderExecutionService`에서 분리한 별도 `@Service` 빈. 지정가 주문의 체결 조건(매수: 현재가 ≤ 지정가, 매도: 현재가 ≥ 지정가) 검사 및 체결 처리
- `MarketPriceEvent`를 `order.support.event`가 아닌 `trading.support.event`로 이동 — Reservation 도메인도 동일 이벤트를 사용하기 때문에 도메인 간 공유 패키지로 이동
- 지정가 체결은 Market 서비스 시세 이벤트 수신 시점마다 조건을 확인하는 방식(이벤트 드리븐)

**3. `EncryptedPayloadConverter` 전 도메인 적용**
- Account / Order / Reservation 세 도메인의 `IdempotencyRecord.responsePayload` 필드에 `@Convert(converter = EncryptedPayloadConverter.class)` 적용
- 각 서비스의 `@Configuration` 클래스에서 `EncryptedPayloadConverter.initKey(base64Key)` 호출 — Spring DI 불가 문제(`common` 모듈 컴포넌트 스캔 범위 밖, Hibernate가 기본 생성자로 직접 인스턴스화)를 정적 홀더 패턴으로 해결한 구조를 실제 서비스에 연결

**4. 배치 담당자 작업 요청 문서 작성**
- `trading-service`가 gRPC로 노출하는 배치용 RPC 4개를 정리해 배치 담당자에게 넘길 작업 요청 이슈 작성: `ProcessOpenLimitReservations`(08:30), `ProcessOpenMarketReservations`(09:00), `ExpirePendingOrders`(15:30), `ProcessTodayCloseReservations`(15:40)

#### [느낀 내용]

* `MarketPriceEvent`를 `order.support.event`에서 `trading.support.event`로 옮긴 결정이 작은 것 같지만, "이 이벤트가 Order 도메인 것인가, 아니면 여러 도메인이 공유하는 것인가"를 명확히 구분한 결과였다. 도메인 경계를 패키지 구조로 표현하는 게 처음엔 과한 것 같아 보여도 나중에 공유 자원이 생겼을 때 이미 위치가 정해져 있으면 혼선이 없다는 걸 체감했다.
* 배치 요청 문서를 작성하면서 내가 구현한 RPC를 다른 사람의 시선으로 다시 설명하는 작업이 의외로 유익했다. 코드는 짰지만 "이게 어떤 순서로, 어떤 상태 전이를 일으키는지"를 글로 쓰다 보니 초안에서 틀렸던 부분(상태 전이 설명, 응답 필드명)이 바로 눈에 띄었다. 구현을 문서화하는 과정이 구현 자체를 검증하는 효과도 있다는 걸 느꼈다.
* 프로젝트 분석 양식을 채우면서 약 2주간 진행한 작업을 한 눈에 보게 됐다. 이슈 단위로 짤 때는 개별 작업처럼 느껴졌던 것들이 전체로 보니 Account → Order → Execution → Reservation → Batch 흐름으로 일관된 방향이 있었다는 걸 알게 됐다. 작업하는 도중엔 보이지 않던 게 정리하고 나서야 보이는 경험이었다.

#### [활용 방안]

* 도메인 간 공유 이벤트/타입은 처음부터 `support.event` 같은 공유 패키지에 두고, 특정 도메인 패키지에 넣는 건 그 도메인만 쓸 것이 확실할 때만 넣기
* 배치 담당자처럼 다른 서비스 개발자에게 RPC 요청 문서를 넘길 때는 ① 상태 전이 ② 응답 필드명 ③ 멱등성/재시도 안전 여부를 반드시 포함하는 템플릿으로 작성
* 구현이 어느 정도 완성됐을 때 분석 양식 형태로 전체를 정리하는 작업을 루틴으로 넣기 — 개별 이슈 단위에서 보이지 않던 흐름이나 누락이 전체 뷰에서 드러남
* 외부 스키마 의존 항목(Market 서비스 Kafka 이벤트, Auth 서비스 `UserWithdrawn`)은 스키마 확정 즉시 연결할 수 있도록 인터페이스/컨슈머 껍데기를 미리 만들어두는 방식으로 블로킹 최소화
