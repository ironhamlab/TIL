* 단원명 : Spring Boot 프로젝트
* 학습 주제 : Reservation 핵심 배치 로직 완성 & 전 도메인 단위 테스트 작성

---

#### [학습 내용]

**1. 건별 배치 처리 전환 + FAILED/EXPIRED 잔고 처리 (#135)**
- 기존 단일 트랜잭션으로 전체 목록을 처리하던 방식에서 건별 개별 트랜잭션으로 전환 — 하나가 실패해도 나머지에 영향을 주지 않도록 격리
- `FAILED` 전이 시 `reservedAmountKrw > 0`이면 `releaseBalance()` 호출로 선점 잔고 반환 — 잔고가 묶인 채로 상태만 바뀌는 상황 방지
- `EXPIRED` 전이도 동일 패턴 적용 — 마감 시각 초과로 만료된 예약도 잔고 반환 보장

**2. `TradingFeePolicy` 공통화 + `fillMarketOrder` BigDecimal 전환 (#137)**
- 수수료/세금 상수(`FEE_RATE 0.00015`, `TAX_RATE 0.0018`)를 `trading.support.TradingFeePolicy`로 추출해 Order/Reservation 도메인에서 공통 사용
- `long` 연산에서 `BigDecimal`로 전환: `setScale()` + `RoundingMode.DOWN` + `longValueExact()`로 원단위 이하 절사 + 오버플로 방지
- `RoundingMode.DOWN`을 선택한 이유: 금융 도메인에서 수수료 계산은 항상 내림(고객에게 유리한 방향이 아닌, 거래소 기준 절사)

**3. CONVERTING 타임아웃 배치 + `ReservationConvertedConsumer` (#139)**
- `ListStaleConvertingReservations` → `FailStaleConvertingReservation` 흐름: 15:30에 당일 남아있는 CONVERTING 건을 스윕해 FAILED로 전이 + 잔고 반환
- 이 배치가 필요한 이유: Reservation → Order 전환이 비동기 Kafka 흐름이기 때문에 `ReservationDue` 이벤트가 유실되거나 컨슈머가 실패하면 예약이 CONVERTING에 영원히 멈출 수 있음 → 타임아웃 스윕으로 선제 방어
- `ReservationConvertedConsumer`: `ReservationConverted` Kafka 이벤트를 수신해 `markConverted(reservationId, orderId)` 호출 → 예약 상태를 CONVERTED로 전이 + `converted_order_id` 기록

**4. `ReservationDueConsumer` + `placeOrderFromReservation()` (#141)**
- `ReservationDueConsumer`: `ReservationDue` Kafka 이벤트 수신 → `placeOrderFromReservation()` 호출 → Order 생성 + `ReservationConverted` Outbox 발행
- 멱등성 키 패턴: `reservation-due:{reservationId}` — 동일 이벤트가 재전달돼도 중복 주문 생성 방지
- 이 컨슈머가 실패하면 Kafka at-least-once 보장에 의해 재전달 → 멱등성 키로 중복 방어, 최종적으로 성공하거나 CONVERTING 타임아웃 배치가 정리

**5. 단위 테스트 전 도메인 작성 (9개 파일 + Consumer 6개 + GrpcService 3개 등)**
- 커버리지 대상: `AccountEntity`, `DefaultAccountService`, `OrderEntity`, `DefaultOrderService`, `DefaultOrderExecutionService`, `OrderLimitFillExecutor`, `ReservationEntity`, `DefaultReservationService`, `ReservationBatchExecutor`, `DefaultReservationBatchService`(배치 루프), 6개 Kafka 컨슈머, `AccountGrpcService`/`OrderGrpcService`/`ReservationGrpcService`(ErrorCode → gRPC Status 전 분기), `IdempotencyExecutor`, `IdempotencyServerInterceptor`
- GrpcService 테스트는 `@ParameterizedTest` + `@EnumSource`로 ErrorCode 전 케이스를 exhaustive하게 검증 — switch문 누락 분기를 테스트로 강제
- 테스트 작성 중 발견한 production code 이슈: `toSide()`/`toTiming()`/`toKind()`가 try 블록 안에서 `StatusRuntimeException`을 던지는데 catch는 도메인 예외만 잡음 → 잘못된 enum 값이 들어오면 unhandled exception으로 propagate됨. 별도 이슈로 등록 필요
- `EncryptedPayloadConverterTest`는 `common` 모듈에 이미 존재 확인 후 두 케이스(키 로테이션, 초기화 전 복호화 시도) 추가로만 진행
- Testcontainers 기반 통합 테스트는 Docker 인프라/`build.gradle` 의존성 추가 부담으로 이번 단계에서 제외

**6. 어필 가능한 코드 소재 정리**
- CONVERTING 타임아웃 처리: 분산 시스템에서 비동기 전환 시 발생하는 partial failure를 설계 단계에서 선제 방어한 사례 — 트러블슈팅 면접 소재로 가장 임팩트 높음
- `static volatile SecretKeySpec` 패턴: 프레임워크(Hibernate)가 예상과 다르게 객체를 생성한다는 걸 root-cause 분석으로 찾아내고 우회한 사례
- `IdempotencyOperations<ID, REC>` 제네릭 인터페이스: 스키마 경계 기준으로 "어디서 중복을 허용하고 어디서 추상화할지"를 판단한 트레이드오프 설계

#### [느낀 내용]

* CONVERTING 타임아웃 배치를 짜면서 "이게 없으면 어떻게 되는가"를 처음으로 끝까지 추적해봤다. Kafka 이벤트 유실 → 컨슈머 재시작 불가 → 예약이 영원히 CONVERTING 상태 → 잔고가 영원히 묶임. 비동기로 서비스 경계를 끊는 결정 자체가 이런 복구 경로를 설계할 책임을 같이 가져온다는 걸 구조적으로 이해했다.
* production code 버그를 테스트 작성 중에 발견한 게(`toSide()`/`toKind()`의 `StatusRuntimeException` 누수) 인상 깊었다. 테스트가 "기능이 작동하는가"를 검증하는 것 외에 "예외 경로가 의도대로 흐르는가"도 검증한다는 걸 실감했다.

#### [활용 방안]

* 비동기 Kafka 흐름으로 서비스 경계를 끊을 때는 항상 "이 이벤트가 유실되거나 컨슈머가 영구 실패하면 어떤 상태가 남는가"를 설계 단계에서 함께 따지고, 타임아웃 스윕 배치 또는 데드레터 큐(DLQ) 처리를 같이 설계하는 걸 기본 패턴으로 삼기
* `BigDecimal` 수수료 계산 패턴(`RoundingMode.DOWN` + `longValueExact()`)은 금융 도메인에서 수치 계산이 필요한 모든 곳에 동일하게 적용 — `long` 직접 계산은 오버플로와 절사 방향을 보장할 수 없음
* GrpcService ErrorCode 분기 테스트는 `@ParameterizedTest` + `@EnumSource`로 exhaustive하게 작성하는 것을 표준 패턴으로 — switch 누락이 테스트 레벨에서 강제로 드러남
* `toSide()`/`toTiming()`/`toKind()`의 `StatusRuntimeException` 누수 이슈는 별도 이슈로 등록해서 try-catch 구조 수정 또는 유효성 검증 레이어 추가로 처리
* 포트폴리오/면접 대비로 CONVERTING 타임아웃 → `static volatile` 패턴 → 멱등성 인터페이스 순서로 트러블슈팅 스토리를 STAR 포맷으로 정리해두기
