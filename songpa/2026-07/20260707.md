* 학습 주제 : 전체 코드 흐름 재정리 & 3개 서비스 기술 문서화

---

#### [학습 내용]

**1. trading-service 전체 코드 흐름 파악 (IntelliJ Ctrl+Click 기준)**
- 코드베이스를 6개 흐름으로 분류: gRPC Account 동기 흐름, Order 접수 및 체결 흐름, Kafka 시세 컨슈머 흐름, Reservation 비동기 흐름, Account 자동 생성 컨슈머 흐름, 횡단 관심사(멱등성/Outbox)
- 3개 도메인이 공유하는 5계층 패턴 확인: `*GrpcService` → `*Service` → `*Repository` → `*Entity` → Outbox 발행. Account(가장 단순)부터 읽고 Order → Reservation 순으로 진행하는 게 패턴을 먼저 내면화하는 데 유리
- Reservation 흐름에서 비직관적인 포인트 확인: `ReservationDueConsumer`가 gRPC 진입점을 거치지 않고 `OrderService`를 직접 내부 호출함 — Ctrl+Click으로 따라가면 gRPC stub이 아니라 서비스 빈이 나오기 때문에 처음 보면 흐름이 끊긴 것처럼 보임


**2. 온보딩 문서 작성**
- trading-service 에 대해 비개발자도 읽을 수 있는 수준의 구조 설명 문서 작성 — 비유, ASCII 박스 다이어그램, 코드 스니펫 포함
- 팀 내 신규 합류자나 발표 청중 대상으로 "이 서비스가 왜 존재하고 어떻게 동작하는가"를 설명하는 용도

**3. 주요 아키텍처 패턴 재정리 (문서화 과정)**
- trading-service: 3개 도메인 스키마 분리(`account`/`order_svc`/`reservation`) + Outbox→Kafka 폴링 릴레이 + 응답 페이로드 암호화 + Reservation↔Order 전체 비동기(Option C)

#### [느낀 내용]

* 코드 흐름을 처음부터 다시 정리하면서, 내가 짠 코드인데도 "전체 흐름을 한 눈에 그릴 수 있는가"와 "각 파일이 어떤 역할인지 설명할 수 있는가"는 다른 문제라는 걸 느꼈다. 구현할 때는 이슈 단위로 쪼개서 짜기 때문에 전체 그림이 머릿속에서 분산돼 있는데, 흐름도로 그려보고 나니 훨씬 더 잘 이해되고 흐름이 잘 연결됐다.
* 온보딩 문서화 과정에서 기존 기록을 참고해서 적으려고 하니 구현 과정에서 변경되어 현재 반영사항과 맞지 않는 것들이 바로 드러났다. 개발 후 문서를 재검토하는 과정이 단순히 구현의 사후 정리가 아니라 사실 검증의 역할도 한다는 걸 느꼈다.
* `ReservationDueConsumer`가 gRPC를 거치지 않고 `OrderService`를 직접 호출한다는 걸 이번에 코드 흐름으로 다시 짚으면서, 이게 왜 그런지를 설명할 수 있어야 한다는 걸 느꼈다. "같은 서비스 내에서 도메인 간 직접 호출은 gRPC 오버헤드 없이 트랜잭션 경계를 명확히 제어하기 위한 선택"이라는 게 이번에 확실히 정리됐다.
* 다른 팀원들이 짠 서비스 문서들을 읽어보며 다른 서비스들은 어떤 방식으로 설계 결정을 달리 했는지가 보여 흥미로웠다. 또한 온전히 한 서비스의 설계부터 구현까지 독립적으로 할 수 있는 마이크로 서비스의 매력을 다시금 느끼게 되었다.

#### [활용 방안]

* 새 도메인이나 서비스를 이해할 때 "6개 흐름으로 분류해서 가장 단순한 것부터" 접근하는 방식을 앞으로도 적용 — Account → Order → Reservation 순서로 읽은 게 효과적이었던 것처럼, 진입점이 명확하고 단순한 흐름부터 패턴을 익히고 복잡한 흐름으로 확장
* 문서화 시 "당연히 그렇겠지"라고 넘긴 사실들(금액, 상태값, 구현 완료 여부)을 명시적으로 코드에서 재확인하는 단계를 포함하기
* 서비스 간 멱등성 처리 방식 비교(trading-service: 전용 레코드 테이블 + 응답 재사용 가능 vs wishlist-service: unique index + 재시도 시 응답 재사용 불가)를 포트폴리오 설계 결정 근거 설명 자료로 활용
