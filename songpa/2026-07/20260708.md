* 단원명 : Spring Boot 프로젝트
* 학습 주제 : 데모 직전 버그 수정

---

#### [학습 내용]


**1. 지정가 즉시 체결 누락 버그 수정 (hotfix/order)**
- 지정가 주문이 이미 조건을 만족하는 가격에 들어왔을 때 즉시 체결되지 않고 다음 시세 틱까지 PENDING으로 남는 버그 발견
- `DefaultOrderService.placeOrder()` LIMIT 분기에 체결 조건 확인 로직이 없었음이 원인 — `fillLimitOrderIfConditionMetOnPlacement()` 메서드 신설해 `placeOrder` / `amendOrder` / `placeOrderFromReservation` 세 진입점에 연결
- `V20260708_001` 마이그레이션이 존재하지 않는 인덱스명(`idx_orders_unique_pending`)을 DROP 시도해 기존 `uq_orders_account_symbol_pending`이 그대로 남아 있던 문제도 함께 발견 → `V20260708_002` 정정 마이그레이션 작성


**2. Market 서비스 Kafka/Redis 구현체 정리**
- Redis Pub/Sub(`market:quotes` 채널) 사용할 수 있도록 코드 추가
- Kafka/Redis 두 구현체를 모두 코드에 보존하되 Kafka 쪽만 `@Component`로 활성화하는 방식으로 정리
- Kafka 토픽명 `market.open-price.v1` → `market.order-book.v1`로 정정


**3. 데모 QA 계획 수립 & 프론트엔드 로그인 정리**
- 데모 5분 기준 타임 스크립트 작성: 삼성전자(005930)로 체결 완료 흐름, SK하이닉스(000660)로 PENDING 상태 시연, 삼성SDI(006400)로 예약 취소/정정 시나리오 사전 세팅
- 지정가 가격 포지션 4가지 케이스(매수 가격 > 현재가 / ≤ 현재가, 매도 가격 < 현재가 / ≥ 현재가) 포함

#### [느낀 내용]

* `V20260708_001` 마이그레이션이 잘못된 인덱스명을 DROP 시도하고 조용히 넘어간 건, 실행은 됐지만 의도한 변경은 적용되지 않은 "침묵하는 실패"였다. Flyway 마이그레이션은 체크섬만 통과하면 성공으로 처리되기 때문에, SQL이 실제로 의도한 대로 동작했는지를 명시적으로 검증하지 않으면 이런 문제가 데모 당일까지 안 보일 수 있다는 걸 직접 경험했다.
* 지정가 즉시 체결 누락은 "지정가는 나중에 체결되는 것"이라는 무의식적인 가정이 코드에 그대로 반영된 결과였다. 정책상 이미 조건을 만족하는 가격으로 들어온 지정가는 즉시 체결되어야 하는데, 그 케이스를 처음부터 빠뜨렸다. 요구사항을 구현할 때 "이 조건이 진입 시점에도 성립할 수 있는가"를 항상 같이 따져야 한다는 걸 다시 느꼈다.

</br>

#### [활용 방안]

* Flyway 마이그레이션 작성 후 "실제로 의도한 DDL이 적용됐는가"를 `\d table_name`이나 `pg_indexes` 조회로 명시적으로 검증하는 단계를 루틴으로 추가
* 주문 진입 시점에 조건 즉시 평가가 필요한 로직(`fillLimitOrderIfConditionMetOnPlacement` 패턴)은 amendOrder / placeOrderFromReservation 등 모든 진입점에 빠짐없이 연결됐는지 체크리스트에 포함
