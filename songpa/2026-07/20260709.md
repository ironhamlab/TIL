#### [학습 내용]

**1. `ReservationBatchService` 실행 흐름 및 상태 전이 완전 정리**
- `ReservationStatusValue` 전체 상태: `RESERVED → CONVERTING → EXECUTED` (정상 경로) + 단말 상태 `CANCELLED / FAILED / EXPIRED`
- `Reservation.EXECUTED` ≠ 거래 체결. OPEN+LIMIT 케이스에서는 "Order로 전환 완료"를 의미하며 실제 체결 여부는 `OrderStatusValue`(PENDING → FILLED)로 별도 추적
- OPEN+LIMIT만 `ReservationDue` Kafka 이벤트 → `ReservationDueConsumer` → `placeOrderFromReservation()` → `ReservationConverted` → `markConverted()` 경로를 거쳐 `Order` 엔티티를 생성함. OPEN+MARKET / PREV_CLOSE / TODAY_CLOSE는 별도 `Order` 엔티티 없이 Reservation 도메인 안에서 `markExecuted()`로 자기완결
- `OrderStatus.REJECTED`는 proto와 스키마에 존재하지만 애플리케이션 레이어에서 REJECTED로 전이하는 진입 경로 없음 — 질문받으면 "구현 갭"으로 솔직하게 인정
- 잔고 보상 트랜잭션: `releaseBalanceInNewTransaction()`이 `REQUIRES_NEW`로 `finally` 블록에서 실행되며 실패 시 `RuntimeException`을 throw해 배치 재시도를 강제

**2. Spring AOP 프록시 메커니즘 심화 이해**
- Spring이 `@Transactional`, `@Async` 등의 부가 기능을 적용하는 방식 = 빈을 직접 반환하지 않고 프록시 객체로 감싸서 반환. 외부에서 메서드를 호출하면 프록시가 가로채지만, 같은 객체 내에서 `this.method()`를 호출하면 프록시를 건너뜀(self-invocation)
- `ReservationBatchExecutor`를 별도 `@Service` 빈으로 분리한 이유: `@Transactional` self-invocation 방지 목적
- AOP 프록시가 적용되는 다른 사례들: `@Transactional`, `@Async`, `@Cacheable`, `@Retry`, Spring Security의 메서드 보안(`@PreAuthorize`) 등 — 모두 같은 프록시 기반 메커니즘을 공유
- 발표 Q&A에서 "왜 별도 빈으로 쪼갰나"라는 질문에 "프록시 기반 AOP의 self-invocation 제약 때문"으로 명확하게 설명 가능하도록 준비

**3. 설계 트레이드오프 13개 항목 Q&A 스크립트 작성**
- 주요 항목: 비관적 락(충돌 자체 방지 × → DB 레벨 접근 순서 제어 ○), Outbox 패턴(유실 없이 복구 × → 재처리 가능한 구조 ○), 예약 비동기(전부 Kafka × → 트리거·상태확정은 이벤트 / 내부 Order 호출은 직접 ○), BigDecimal + RoundingMode.DOWN, Jackson 3.x 전환 등

#### [활용 방안]

* 새 기능을 구현한 후 "이 기능을 3문장으로 설명할 수 있는가"를 구현 완료 기준에 포함하기 — 말로 설명 안 되는 건 아직 이해가 덜 된 것
* 설계 트레이드오프는 "A를 채택 → 대안 B → A의 이유 / B의 한계" 3단 포맷으로 기록해두는 습관 → 다음 프로젝트의 설계 문서나 면접 답변에 바로 재사용 가능
* Spring AOP가 적용되는 어노테이션(`@Transactional`, `@Async`, `@Cacheable`, `@PreAuthorize` 등)은 모두 "외부 호출은 프록시가 가로채고, 내부 self-invocation은 가로채지 못한다"는 동일 원칙이 적용됨 → 해당 어노테이션을 추가할 때마다 self-invocation 가능성을 먼저 체크
