* 단원명 : LLM
* 학습 주제 : VectorStore, Fast API

#### [학습 내용]

1. **VectorStore와 RAG 구조**
* Embedding, VectorStore, Retriever, RAG, Memory의 역할을 명확하게 구분했다.
* VectorStore는 Vector만 저장하는 것이 아니라 Document의 원문, ID, metadata까지 함께 관리하여 검색 결과를 LLM에 전달하기 위한 저장소라는 점을 이해했다.
* Retriever는 VectorStore에서 어떤 기준(top_k, filter 등)으로 검색할지 결정하는 역할이며, RAG는 검색된 문서를 Context로 사용하는 전체 답변 구조임을 학습했다.
* Memory는 사용자 정보와 이전 대화를 관리하는 역할이며, 외부 지식을 검색하는 RAG와는 책임이 다르다는 점을 이해했다.

2. **VectorStore 검색 과정**

* 문서와 질문을 동일한 Embedding 모델로 벡터화한 뒤 Cosine Similarity를 이용해 의미적으로 가까운 문서를 검색하는 과정을 실습했다.
* LangChain의 `InMemoryVectorStore`를 이용하여

  * Document 저장(add)
  * Similarity Search
  * Metadata Filter
  * Delete
    기능을 직접 사용해 보았다.
* 직접 Cosine Similarity를 구현한 방식과 VectorStore를 사용하는 방식을 비교하면서, VectorStore가 Embedding 생성, Document 관리, 검색 과정을 하나의 인터페이스로 제공한다는 점을 확인했다.

3. **VectorStore 선택 기준**

* InMemory, FAISS, Chroma, pgvector, Qdrant, Pinecone 등 다양한 VectorStore를 비교했다.
* 데이터 규모, 영속성, 동시성, 기존 DB 사용 여부, 운영 비용을 기준으로 적절한 저장소를 선택해야 한다는 점을 배웠다.

4. **RAG와 Memory 결합**

* VectorStore에서 검색한 결과를 Prompt의 RAG Context로 전달하고,
* Memory에는 사용자 수준이나 이전 대화만 저장하여 두 정보를 분리하는 구조를 학습했다.
* 검색어에는 외부 지식만 포함하고, 사용자 정보는 Memory에서 가져오는 것이 검색 품질을 높이는 방법이라는 점을 이해했다.

---

5. **FastAPI 기초**

* FastAPI가 Python 함수를 HTTP API로 제공하는 웹 프레임워크라는 점을 학습했다.
* Uvicorn을 이용한 서버 실행 방법과 요청이 처리되는 전체 흐름을 이해했다.
* Path Parameter, Query Parameter, Request Body의 역할과 사용 목적을 구분할 수 있게 되었다.
* Pydantic의 BaseModel과 Field를 이용하여 입력 검증을 수행하고, 검증 실패 시 422 응답이 발생하는 이유를 이해했다.
* Response Model을 이용하여 필요한 데이터만 응답으로 반환하고, 내부 데이터(password 등)를 숨길 수 있다는 점을 확인했다.
* APIRouter를 이용해 API를 기능별로 분리하고 OpenAPI와 Swagger 문서가 자동 생성되는 구조를 학습했다.
* CORS가 브라우저 보안 정책이며 서버 간 통신에는 적용되지 않는다는 점을 이해했다.

#### [느낀 내용]

* LLM 서비스 구조와 웹 서버 구조가 연결되는 지점을 이해했다.

* 이전에는 Embedding, RAG, Memory를 각각 개별 개념으로 학습했는데, 오늘은 VectorStore → Retriever → RAG → LLM 흐름과 Browser → FastAPI → Pydantic → Python 함수 흐름이 하나의 서비스 안에서 어떻게 이어지는지 볼 수 있었다.

* FastAPI의 Pydantic 검증과 response_model 기능이 단순 편의 기능이 아니라 API 계약을 강제하고 보안을 높이는 역할까지 한다는 점을 알게 되었다.
