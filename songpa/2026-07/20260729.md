* 단원명 : LLM
* 학습 주제 : Agentic AI

#### [학습 내용]

* **Workflow와 Agent의 차이**

  * Workflow는 개발자가 Python의 조건문 등을 이용해 사용할 Tool과 실행 순서를 미리 결정하는 방식이라는 점을 학습했다.
  * Agent는 OpenAI 모델이 사용자의 질문과 Tool Schema를 확인한 뒤 실행 중에 필요한 Tool과 호출 순서를 스스로 결정하는 방식이라는 점을 이해했다.
  * 장소 검색, 예산 계산, 일반 인사, 복합 요청을 각각 실행하여 Workflow와 Agent가 Tool을 선택하는 과정을 비교했다.
  * 복합 요청에서는 Agent가 하나의 Tool만 사용하는 것이 아니라 질문 해결에 필요한 여러 Tool을 함께 호출할 수 있다는 점을 확인했다.
  * Tool이 필요하지 않은 질문에는 모델이 Tool을 호출하지 않고 직접 답변할 수 있다는 점을 학습했다.

  </br></br>

* **LangChain Tool과 Tool Schema**

  * 일반 Python 함수와 LangChain Tool 객체의 차이를 학습했다.
  * 일반 함수는 직접 실행할 수 있지만, 모델이 함수의 이름, 역할, 입력 형식을 알 수 없다는 점을 이해했다.
  * `@tool`을 이용하면 함수에 Tool 이름, 설명, 입력 Schema가 추가되어 모델이 함수의 사용 방법을 판단할 수 있다는 점을 확인했다.
  * Pydantic의 `BaseModel`과 `Field`를 이용해 Tool이 받을 입력값의 이름, 타입, 설명을 정의하는 방법을 실습했다.
  * Tool의 이름, 설명, JSON Schema가 모델과 Tool 사이의 실행 계약 역할을 한다는 점을 이해했다.

  </br></br>

* **Schema 검증과 업무 규칙 검증**

  * Tool 입력값 검증을 Schema 검증과 함수 내부의 업무 규칙 검증으로 나누어 처리하는 방법을 학습했다.
  * 필수 입력값 누락이나 잘못된 타입은 Pydantic Schema가 함수 실행 전에 검증한다는 점을 확인했다.
  * 여행 인원이 1명 이상인지, 입장료와 식비가 0원 이상인지와 같은 도메인 규칙은 함수 내부에서 검증해야 한다는 점을 이해했다.
  * 검색 결과가 없다는 것은 입력값 검증 실패가 아니라 Tool이 정상적으로 실행한 결과라는 점을 구분했다.
  * 입력 검증 오류와 정상적인 검색 실패를 서로 다른 상황으로 처리해야 한다는 점을 학습했다.

  </br></br>

* **Agent의 Tool Calling 메시지 흐름**

  * Agent가 Tool을 호출할 때 생성되는 `HumanMessage`, `AIMessage`, `ToolMessage`의 역할을 학습했다.
  * `HumanMessage`에는 사용자의 질문이 저장되고, Tool 호출이 포함된 `AIMessage`에는 Action 정보가 저장된다는 점을 확인했다.
  * `ToolMessage`에는 Tool의 실행 결과인 Observation이 저장되고, 마지막 `AIMessage`에는 최종 답변이 저장된다는 점을 이해했다.
  * `tool_call_id`를 통해 모델이 요청한 Tool 호출과 실제 Tool 실행 결과가 연결된다는 점을 학습했다.
  * 예상한 Tool과 실제 Agent가 호출한 Tool을 비교하여 Tool Calling 결과를 검증하는 방법을 실습했다.
  * 복수 Tool 요청에서는 호출 순서보다 필요한 Tool이 모두 사용되었는지를 집합으로 비교하는 방법을 익혔다.

  </br></br>

* **ReAct 기반 Agent 실행 구조**

  * ReAct가 Action과 Observation을 반복하면서 다음 행동을 결정하는 구조라는 점을 학습했다.
  * 모델이 Tool을 호출하면 Tool 실행 결과를 다시 읽고, 추가 호출이나 최종 답변 중 다음 행동을 선택하는 과정을 이해했다.
  * LangGraph의 `MessagesState`, `ToolNode`, `tools_condition`을 이용해 모델과 Tool 사이를 반복하는 Agent Graph를 구현했다.
  * `tools_condition`은 Tool 실행의 성공 여부를 판단하는 것이 아니라, 마지막 AI 메시지에 Tool 호출이 있는지를 확인해 Tool Node 또는 종료 경로를 선택한다는 점을 학습했다.
  * Tool 실행 후 다시 Agent Node로 이동하도록 Edge를 연결하여 여러 번의 Action과 Observation이 가능하도록 구성했다.

  </br></br>

* **Tool 실패 후 회복과 재시도**

  * 첫 번째 검색 결과가 부족할 때 Agent가 Observation을 확인하고 검색 조건을 변경해 다시 Tool을 호출하는 구조를 실습했다.
  * 첫 검색은 `strict` 모드로 수행하고, 결과가 `NOT_FOUND`이면 핵심 조건만 남겨 `broad` 모드로 재검색하도록 구성했다.
  * Tool 결과에 `retry_hint`를 포함하여 Agent가 다음 행동을 결정할 때 참고하도록 설계했다.
  * `strict → broad`로 검색 전략이 변경되었는지, `NOT_FOUND` 이후 `FOUND` 결과가 발생했는지를 실행 메시지로 검증했다.
  * 실패했다고 무조건 종료하지 않고, Observation을 근거로 Tool 인자를 수정해 회복할 수 있다는 점을 이해했다.

  </br></br>

* **정보 부족 시 추가 질문 처리**

  * 예산 계산에 필요한 인원, 입장료, 식비 중 일부가 없을 때 값을 추측하지 않도록 Agent 규칙을 설정했다.
  * 필수 정보가 부족한 경우 Tool을 호출하지 않고 사용자에게 추가 정보를 요청하도록 구성했다.
  * 정보 부족 상황에서 실제 Tool 호출 수가 0인지 확인하여 Agent가 규칙을 올바르게 따랐는지 검증했다.
  * Tool 호출이 가능한지 판단하는 것도 Agent의 중요한 역할이라는 점을 이해했다.

  </br></br>

* **Checkpointer를 이용한 Thread별 대화 기억**

  * LangGraph의 `InMemorySaver`를 Checkpointer로 사용하여 같은 `thread_id`의 대화 상태를 이어서 저장하는 방법을 학습했다.
  * 같은 Thread에서 전달한 이름, 동행인, 전체 예산 정보를 다음 요청의 Tool 인자로 사용하는 구조를 구현했다.
  * 사용자가 전체 예산을 수정하면 이후 Tool 호출에서 기존 값이 아니라 가장 최근 값을 사용하도록 구성했다.
  * 서로 다른 `thread_id`를 사용하면 이전 대화 정보가 공유되지 않고 독립적으로 관리된다는 점을 확인했다.
  * 다른 Thread에서 필수 정보가 없을 경우 Agent가 값을 추측하지 않고 추가 질문을 하도록 설정했다.
  * Checkpoint에 저장된 메시지와 사용자 입력을 직접 조회하여 Thread별 상태가 실제로 유지되는지 검증하는 방법을 익혔다.

  </br></br>

* **대화 기억을 활용한 Tool 인자 생성**

  * Agent가 현재 질문에 포함된 값뿐만 아니라 이전 대화 메시지에서 필요한 정보를 찾아 Tool 인자를 구성하는 과정을 학습했다.
  * 여행자 이름, 동행인, 전체 예산이 모두 존재할 때만 장소 추천 Tool을 호출하도록 구현했다.
  * Tool 호출 인자에 이름, 동행인, 예산이 정확히 반영되었는지 각각 비교하여 검증했다.
  * 대화 메시지를 기억하는 것과 구조화된 Profile을 별도로 저장하는 것은 다른 방식이라는 점을 확인했다.
  * 현재 실습에서는 별도의 Profile 필드 없이 Checkpoint의 메시지 기록을 모델이 읽어 필요한 정보를 추출한다는 점을 이해했다.

</br></br></br>

#### [느낀 내용]

* Workflow와 Agent의 차이는 단순히 자동화 여부가 아니라 누가 실행 순서와 Tool 선택을 결정하는지에 있다는 점을 이해했다.

* Tool을 단순한 Python 함수로 만드는 것보다 이름, 설명, 입력 Schema를 명확히 작성하는 것이 Agent의 정확한 Tool 선택과 인자 생성에 중요하다는 점이 인상적이었다.

* Agent가 한 번 Tool을 호출하고 끝나는 것이 아니라 Tool 결과를 Observation으로 다시 읽고, 실패 원인에 따라 검색 조건을 바꾸거나 추가 질문을 선택할 수 있다는 점에서 일반적인 고정형 Workflow와의 차이를 확인할 수 있었다.

* 필요한 정보가 부족할 때 임의로 값을 추측하지 않고 사용자에게 다시 질문하도록 만드는 것도 Agent 품질을 결정하는 중요한 설계 요소라고 느꼈다.

* Checkpointer를 이용하면 같은 사용자의 이전 대화를 이어서 활용하면서도 `thread_id`별로 상태를 분리할 수 있어, 개인화된 AI 서비스의 기본 구조로 활용할 수 있을 것이라고 생각했다.

</br>

#### [활용 방안]

* 실행 순서가 명확하고 변하지 않는 작업은 Workflow로 구현하고, 질문에 따라 Tool 선택과 실행 순서가 달라지는 작업은 Agent로 구현하기

* Agent용 Tool을 만들 때 함수 이름, 설명, 입력 Schema를 구체적으로 작성하여 모델이 Tool의 목적과 인자를 정확하게 이해하도록 구성하기

* 필수 필드와 타입은 Pydantic Schema에서 검증하고, 인원수나 금액 범위와 같은 업무 규칙은 Tool 함수 내부에서 검증하기

* Agent 실행 과정을 `HumanMessage → AIMessage(Action) → ToolMessage(Observation) → AIMessage(Final Answer)` 순서로 추적하여 Tool Calling 오류를 분석하기

* Tool 실행 결과가 부족할 때 재시도 조건과 `retry_hint`를 제공하여 Agent가 인자를 수정하고 회복할 수 있도록 설계하기

* 필요한 정보가 부족한 경우 값을 추측하지 않고 Tool 호출을 중단한 뒤 사용자에게 추가 질문을 하도록 규칙 설정하기

* Checkpointer와 `thread_id`를 이용하여 사용자별 대화 상태를 유지하고, 수정된 최신 정보를 다음 Tool 호출에 반영하기

* 향후 프로젝트에서는 대화 메시지 기반 기억과 별도의 구조화된 Profile State를 비교하여 사용자 정보 관리 방식을 설계하기
