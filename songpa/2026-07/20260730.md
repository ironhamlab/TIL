* 단원명 : LLM
* 학습 주제 : Agentic AI, WorkFlow

---

#### [학습 내용]

* **Planner를 이용한 목표 분해**

  * 사용자의 자연어 목표를 실행 가능한 Task 목록으로 분해하는 Planner 구조를 학습했다.
  * `ChatOpenAI.with_structured_output(Plan)`을 이용하여 LLM이 자유 형식 문장이 아니라 정해진 `Plan` 객체를 반환하도록 구성했다.
  * `requirements`, `weather`, `destination`, `budget`, `compose`처럼 미리 등록된 Task 중 목표 해결에 필요한 작업만 선택하도록 프롬프트를 작성했다.
  * 단순히 비용만 계산하는 요청과 전체 하루 일정을 만드는 요청을 비교하여 목표에 따라 필요한 Task의 개수와 순서가 달라질 수 있다는 점을 확인했다.
  * 모든 요청이 항상 같은 순서로 실행된다면 고정 Workflow로도 충분하지만, 목표마다 필요한 작업이 달라진다면 Planner가 유용하다는 점을 이해했다.

  </br></br>

* **구조화된 Plan 계약과 검증**

  * `Plan` 모델을 이용하여 Planner와 Executor가 공유하는 실행 계약을 정의했다.
  * `Literal`을 사용해 Planner가 선택할 수 있는 Task 이름을 등록된 값으로 제한했다.
  * 등록되지 않은 Task가 포함된 Plan은 Pydantic 검증 단계에서 차단되도록 구성했다.
  * `field_validator`를 이용해 동일한 Task가 중복으로 포함되지 않도록 검사했다.
  * `goal`, `tasks`, `success_criteria`의 길이와 개수를 제한하여 실행할 수 없는 Plan이 다음 단계로 전달되지 않도록 했다.
  * LLM이 생성한 결과도 다시 `Plan.model_validate()`로 검증하여 구조화된 출력이라고 해도 애플리케이션에서 재검증해야 한다는 점을 학습했다.

  </br></br>

* **여행 도메인 모델 구조화**

  * `TripRequest`, `Place`, `ItineraryDraft`, `ValidationReport`를 Pydantic 모델로 정의하여 여행 계획에 필요한 데이터를 구조화했다.
  * `TripRequest`에는 날씨, 인원수, 전체 예산, 아이 동반 여부를 저장하고 각 필드의 허용 범위를 검증했다.
  * `Place`에는 장소명, 실내 여부, 아이 친화 여부, 1인 입장료를 저장했다.
  * `ItineraryDraft`에는 선택 장소, 실내 여부, 아이 친화 여부, 예상 비용, 요약을 저장했다.
  * `ValidationReport`를 통해 실행 결과의 성공 여부와 실패 조건을 함께 관리하는 방법을 익혔다.
  * 문자열과 딕셔너리만 사용하는 것보다 명확한 도메인 모델을 사용하면 Planner, Executor, Validator 간 데이터 계약을 안정적으로 유지할 수 있다는 점을 이해했다.

  </br></br>

* **Task별 실행 함수와 Context 관리**

  * Planner가 선택한 Task 이름을 실제 실행 함수와 연결하기 위해 `TASK_HANDLERS` 매핑을 구성했다.
  * `requirements`, `weather`, `destination`, `budget`, `compose` Task마다 하나의 실행 함수를 연결했다.
  * 각 실행 함수가 공통 `Context`에 자신의 처리 결과를 저장하도록 구현했다.
  * 요구사항 확인 결과, 날씨 정책, 장소 후보, 예산 계산 결과, 일정 초안을 서로 다른 Context Key로 관리했다.
  * 이전 Task가 만든 결과를 다음 Task가 읽는 방식으로 실행 단계 사이의 의존성을 구성했다.
  * Planner가 생성한 Task 순서대로 실행 함수를 호출하고 실제 실행된 Task를 `path`에 기록하는 방법을 학습했다.

  </br></br>

* **Executor를 이용한 Plan 실행**

  * Executor가 검증된 Plan을 받아 Task 순서대로 실제 함수를 호출하는 구조를 학습했다.
  * `execute_plan()`에서 Plan의 각 Task를 `TASK_HANDLERS`로 조회하고 해당 실행 함수를 순차적으로 호출했다.
  * 실행 중 생성된 Context와 일정 Draft를 State에 저장하여 다음 Node가 사용할 수 있도록 구성했다.
  * 전체 일정 생성 요청에서는 `compose` Task가 반드시 필요하며, Draft가 만들어지지 않은 경우 실행 오류를 발생시키도록 했다.
  * Planner는 무엇을 실행할지 결정하고 Executor는 실제 작업을 수행한다는 역할 분리를 이해했다.
  * LLM이 직접 모든 작업을 수행하는 것이 아니라 등록된 함수만 선택하고 실행하도록 제한할 수 있다는 점을 학습했다.

  </br></br>

* **여행 조건에 따른 장소 검색과 비용 계산**

  * 날씨와 아이 동반 여부를 기준으로 장소 목록을 필터링하는 방법을 실습했다.
  * 비가 오는 경우 실내 장소만 남기고, 아이 동반 요청인 경우 아이 친화 장소만 남기도록 구성했다.
  * 각 장소의 입장료와 인원수, 1인당 식비 20,000원, 교통비 5,000원을 이용해 예상 총비용을 계산했다.
  * 장소별 예상 비용이 사용자의 전체 예산 이하인지 `within_budget` 값으로 판단했다.
  * 사용자의 요청값이 변경되면 장소 후보와 예상 비용 결과도 달라지는 구조를 이해했다.
  * 실제 가격이 아닌 학습용 추정값이라는 성격을 유지하도록 결과에 근거와 계산 내용을 포함하는 방법을 익혔다.

  </br></br>

* **검증 가능한 일정 Draft 생성**

  * 예산을 충족하는 장소 중 예상 비용이 가장 낮은 장소를 선택하여 일정 Draft를 생성했다.
  * 선택한 장소의 이름, 실내 여부, 아이 친화 여부, 예상 비용을 구조화된 Draft에 저장했다.
  * 조건과 예산을 만족하는 장소가 없으면 임의의 장소를 선택하지 않고 `selected_place=None`으로 남기도록 구현했다.
  * 실패 상태도 정상적인 데이터 형태로 표현하면 Validator가 구체적인 실패 원인을 판단할 수 있다는 점을 이해했다.
  * 최종 문장만 생성하는 것이 아니라 검증 가능한 필드를 포함한 중간 결과를 만드는 것이 Agentic Workflow에서 중요하다는 점을 학습했다.

  </br></br>

* **Validator를 이용한 결과 검증**

  * Executor의 실행 결과가 사용자의 요청 조건과 Plan의 완료 기준을 만족하는지 검사하는 Validator를 구현했다.
  * Plan에 포함된 Task가 실제로 Context 결과를 생성했는지 확인했다.
  * 선택된 장소가 존재하는지, 비 오는 날 실내 장소인지, 아이 동반이 가능한지, 예상 비용이 예산을 초과하지 않는지 검증했다.
  * 검증에 실패하면 하나의 오류만 반환하는 것이 아니라 모든 실패 조건을 `failed_conditions`에 누적하도록 구성했다.
  * Validator의 결과를 `passed`와 실패 원인 목록으로 분리하여 다음 단계에서 재시도 여부를 판단할 수 있도록 했다.
  * 실행 완료와 목표 달성을 구분해야 하며, 모든 Task가 실행되었다고 해서 결과가 반드시 성공한 것은 아니라는 점을 이해했다.

  </br></br>

* **Planner, Executor, Validator Graph 구성**

  * LangGraph를 이용해 `START → executor → validator → END` 실행 흐름을 구성했다.
  * `LessonState`에 요청, Plan, Context, Draft, 검증 결과, 실행 경로를 저장했다.
  * Executor Node가 Plan을 실행하고 Validator Node가 결과를 평가하도록 역할을 분리했다.
  * Node마다 변경된 State만 반환하고 LangGraph가 전체 State를 이어서 관리하는 방식을 복습했다.
  * 실행 경로를 기록하여 Planner가 선택한 Task와 Graph Node의 실행 순서를 함께 확인하는 방법을 익혔다.

  </br></br>

* **Replanner를 이용한 실패 후 재계획**

  * Validator가 실패를 반환했을 때 실패 원인을 바탕으로 Plan을 수정하는 Replanner 구조를 학습했다.
  * `ReplanDecision` 모델을 이용해 Replanner의 결과를 `retry` 또는 `stop`으로 제한했다.
  * `retry`를 선택한 경우에는 반드시 수정된 Plan을 함께 반환하도록 `model_validator`로 검증했다.
  * 누락된 Task를 추가하면 해결 가능한 문제는 새로운 Plan으로 재시도하고, 예산 부족처럼 Plan 변경으로 해결할 수 없는 문제는 종료하도록 프롬프트를 구성했다.
  * Replanner가 반환한 수정 Plan은 다시 Executor로 전달하고, `stop`을 반환하면 Workflow를 종료하도록 구성했다.
  * 실패 원인을 분석하고 다음 실행 계획을 변경하는 과정이 일반적인 고정 Workflow와 Agentic Workflow의 중요한 차이라는 점을 이해했다.

  </br></br>

* **Conditional Edge와 반복 제어**

  * Validator 결과와 Replanner 판단에 따라 실행 경로를 변경하는 Conditional Edge를 구현했다.
  * 검증 결과가 PASS이면 즉시 종료하고, FAIL이면 Replanner로 이동하도록 구성했다.
  * 재시도 횟수가 `max_retries`에 도달하면 추가 재계획 없이 종료하도록 제한했다.
  * Replanner의 판단이 `retry`이면 Executor로 돌아가고, `stop`이면 종료하도록 구성했다.
  * `recursion_limit`과 `max_retries`를 함께 사용하여 무한 반복을 방지하는 방법을 학습했다.
  * Agentic Workflow에서는 성공 경로뿐 아니라 실패, 재시도, 중단 조건도 명확하게 설계해야 한다는 점을 이해했다.

  </br></br>

* **Planner-Executor-Validator-Replanner 전체 구조**

  * 전체 실행 흐름을 `Planner → Executor → Validator → Replanner` 구조로 구성했다.
  * Planner는 목표를 Task로 분해하고, Executor는 등록된 함수를 실행하며, Validator는 결과를 평가하고, Replanner는 실패 원인에 따라 수정 또는 종료를 결정했다.
  * 각 단계가 하나의 책임만 담당하도록 분리하여 실행 흐름과 오류 원인을 쉽게 확인할 수 있도록 했다.
  * LLM은 Plan과 재계획 같은 판단 작업에 사용하고, 검색과 계산은 정해진 Python 함수로 실행하는 혼합 구조를 이해했다.
  * 모든 작업을 LLM에 맡기지 않고 구조화된 모델과 검증 로직을 함께 사용해야 안정적인 Agentic Workflow를 만들 수 있다는 점을 학습했다.

</br></br></br>

#### [느낀 내용]

* 이전에는 Agent가 질문을 보고 Tool을 선택하는 구조를 주로 학습했지만, 오늘은 목표를 먼저 여러 Task로 분해하고 실행한 뒤 결과까지 검증하는 더 큰 단위의 Agentic Workflow를 이해할 수 있었다.

* Planner가 자유롭게 작업 이름을 만들어내도록 두는 것이 아니라 등록된 Task만 선택하게 하고, Pydantic으로 중복이나 잘못된 Task를 차단하는 과정이 안정적인 실행에 중요하다고 느꼈다.

* Planner가 만든 계획이 그럴듯하더라도 실제 실행 결과가 사용자 조건을 만족하는지는 별도의 Validator가 확인해야 한다는 점이 인상적이었다.

* 조건을 만족하지 못했을 때 바로 실패로 끝내는 것이 아니라, 실패 원인이 누락된 Task 때문인지 예산처럼 해결할 수 없는 조건 때문인지 구분하여 재계획하는 구조가 실제 Agent에 가까운 방식이라고 느꼈다.

* LLM은 판단과 계획에 사용하고, 비용 계산이나 장소 필터링처럼 결과가 명확해야 하는 작업은 Python 함수로 처리하는 것이 정확성과 제어 가능성 측면에서 적절하다고 생각했다.

</br>

#### [활용 방안]

* 사용자의 요청마다 필요한 작업이 달라지는 AI 서비스에서는 Planner를 이용해 목표를 등록된 Task 목록으로 분해하기

* Planner의 출력은 Pydantic 구조화 모델로 제한하고, 등록되지 않은 Task와 중복 Task를 실행 전에 차단하기

* Planner가 선택한 Task 이름과 실제 Python 실행 함수를 명확하게 매핑하여 LLM이 임의의 코드를 실행하지 못하도록 구성하기

* 실행 단계의 중간 결과를 Context에 구조화하여 다음 Task와 Validator가 재사용할 수 있도록 설계하기

* 최종 결과를 문장만으로 생성하지 않고 장소, 예상 비용, 조건 충족 여부처럼 검증 가능한 필드를 포함한 Draft로 만들기

* Executor의 실행 완료 여부와 사용자의 목표 달성 여부를 Validator에서 별도로 검증하기

* 실패 원인이 Task 누락으로 해결 가능한 경우 Replanner가 Plan을 수정하도록 하고, 조건 자체가 해결 불가능한 경우에는 재시도하지 않고 종료하기

* `max_retries`와 `recursion_limit`을 설정하여 재계획 과정에서 무한 반복이 발생하지 않도록 제한하기

* 향후 AI Agent 프로젝트에서 Planner, Executor, Validator, Replanner를 분리하여 실행 과정과 실패 원인을 추적할 수 있는 구조로 구현하기
