* 학습 주제 : LangSmith

#### [학습 내용]

* **LangSmith 환경 변수 설정과 연결 확인**

  * LangSmith Trace 업로드에 필요한 `LANGSMITH_API_KEY`, `LANGSMITH_TRACING`, `LANGSMITH_PROJECT` 환경 변수를 설정하는 방법을 학습했다.
  * `.env`의 값을 `load_dotenv()`로 불러오고, 필수 환경 변수의 누락 여부와 값의 유효성을 검사하는 로직을 구현했다.
  * `LANGSMITH_TRACING` 값이 `true`, `1`, `yes`, `on` 중 하나인지 확인하여 잘못된 추적 설정을 실행 전에 차단하도록 구성했다.
  * 예시 API Key처럼 `your_`로 시작하는 값이 설정된 경우 실제 Key로 변경하도록 오류 메시지를 반환했다.
  * API Key 원문을 출력하지 않고 앞뒤 일부만 표시하는 `masked()` 함수를 이용해 보안 정보를 노출하지 않으면서 설정 여부를 확인했다.
  * `Client().info`를 호출하여 환경 변수 설정뿐 아니라 실제 LangSmith API 서버 연결까지 확인하는 방법을 실습했다.
  * `--run` 옵션을 사용한 경우에만 외부 API 연결을 시도하여 단순 설정 확인과 실제 연결 검사를 분리했다.

  </br></br>

* **LangSmith Trace를 이용한 Workflow 실행 추적**

  * `tracing_context(enabled=True)`를 이용하여 Workflow 실행 과정을 LangSmith에 Trace로 기록하는 방법을 학습했다.
  * LangGraph Workflow 전체를 하나의 실행으로 추적하고, Planner, Executor, Validator의 실행 흐름을 LangSmith 화면에서 확인할 수 있도록 구성했다.
  * `metadata`에 Workflow 버전을 저장하고 `tags`에 `travel-workflow`, `baseline`, `fixed`, `llm` 등의 값을 추가하여 실행 결과를 구분하는 방법을 익혔다.
  * 고정 Plan을 사용하는 실행과 실제 OpenAI Planner를 사용하는 실행을 `--llm` 옵션으로 구분했다.
  * 실행 결과에서 Plan, Path, Draft, Validation을 출력하여 로컬 결과와 LangSmith Trace를 함께 비교할 수 있도록 했다.
  * LangSmith Trace는 최종 답변만 확인하는 것이 아니라 어떤 Plan과 Task 경로를 거쳐 결과가 생성되었는지 관찰하는 데 사용할 수 있다는 점을 이해했다.

  </br></br>

* **`@traceable`을 이용한 세부 Task 추적**

  * `@traceable` 데코레이터를 이용해 Workflow 내부의 각 Task를 개별 Run으로 추적하는 방법을 학습했다.
  * 요구사항 확인, 날씨 분석, 장소 검색, 예산 계산, 일정 작성 함수를 각각 `tool` 타입의 Run으로 기록하도록 구성했다.
  * 전체 Workflow는 `chain` 타입으로 추적하고, 내부 Task는 `tool` 타입으로 추적하여 상위 Run과 하위 Run의 계층 구조를 만들었다.
  * 기존 실행 함수 자체를 수정하기보다 Trace 전용 래퍼 함수에서 원본 함수를 호출하고 결과를 반환하도록 구성했다.
  * 장소 객체나 일정 Draft와 같은 Pydantic 객체를 `model_dump()`로 변환하여 LangSmith에서 확인 가능한 직렬화된 값으로 기록했다.
  * Planner, Executor, Validator가 공유하는 State와 각 Task의 실행 결과를 함께 추적할 수 있도록 Workflow를 구성했다. 

  </br></br>

* **Workflow 버전별 실행 비교**

  * 동일한 Workflow를 `baseline`, `fixed`, `llm`, `runtime_error` 버전으로 나누어 실행하는 방법을 학습했다.
  * `baseline` 버전은 장소 검색 Task가 누락된 Plan을 사용하고, `fixed` 버전은 필요한 Task가 모두 포함된 Plan을 사용하도록 구성했다.
  * `llm` 버전은 고정된 Task 목록 대신 실제 LLM Planner가 목표에 따라 Plan을 생성하도록 구현했다.
  * `runtime_error` 버전은 `compose` Task를 제거하여 Draft가 생성되지 않는 실행 오류를 의도적으로 재현했다.
  * 같은 입력을 서로 다른 버전으로 실행하여 Plan의 차이가 실행 경로와 검증 결과에 어떤 영향을 주는지 비교했다.
  * 버전별 Trace에 서로 다른 Metadata와 Tag를 추가하여 LangSmith에서 수정 전후 실행을 쉽게 구분하도록 했다.
  * 수정 전 코드와 수정 후 코드를 비교할 때 입력 조건은 동일하게 유지하고 Workflow 버전만 변경해야 원인을 정확하게 분석할 수 있다는 점을 이해했다. 

  </br></br>

* **실패 Trace와 Runtime Error 재현**

  * 정상적으로 실행되지만 검증에 실패하는 경우와 실행 중 예외가 발생하는 경우를 구분하여 Trace를 기록했다.
  * 장소 검색 Task가 누락된 `baseline` 버전에서는 Workflow는 끝까지 실행되지만 Validator가 실패 결과를 반환하도록 구성했다.
  * `compose` Task가 누락된 `runtime_error` 버전에서는 Draft가 생성되지 않아 `ValueError`가 발생하도록 구현했다.
  * 예상한 예외가 발생하지 않으면 별도의 `RuntimeError`를 발생시켜 테스트 자체가 잘못 통과하지 않도록 했다.
  * LangSmith에서는 실패한 실행도 Trace로 남기 때문에 어느 Run에서 어떤 예외가 발생했는지 확인할 수 있다는 점을 학습했다.
  * 검증 실패와 Runtime Error는 원인과 대응 방식이 다르므로 평가 및 디버깅 과정에서 구분해야 한다는 점을 이해했다.

  </br></br>

* **Baseline과 Fixed 결과 비교**

  * `WORKFLOW_VERSION` 값에 따라 `baseline_target` 또는 `fixed_target`을 선택해 실행하는 구조를 구현했다.
  * 동일한 입력으로 수정 전후 Workflow를 실행하여 Plan, Path, 선택 장소, Validation 결과를 비교했다.
  * 최종 검증 결과의 `passed` 값을 기준으로 PASS와 FAIL을 출력했다.
  * 단순히 코드가 실행되었다는 사실이 아니라 Validator가 요구사항을 충족했다고 판단했는지를 최종 성공 기준으로 사용했다.
  * LangSmith Trace를 통해 수정 전후 실행을 각각 저장하면 코드 변경으로 실제 품질이 개선되었는지 비교할 수 있다는 점을 이해했다.
  * 수동 실행 결과와 LangSmith에 업로드된 Trace를 함께 확인하는 방식이 Workflow 디버깅에 유용하다고 느꼈다.

  </br></br>

* **LangSmith Dataset 생성**

  * Workflow를 반복적으로 평가하기 위해 입력값과 기대 결과를 LangSmith Dataset으로 저장하는 방법을 학습했다.
  * `EVALUATION_CASES`에 날씨, 인원, 예산, 아이 동반 여부와 기대 PASS/FAIL 결과를 정의했다.
  * 정상적으로 일정을 생성해야 하는 사례와 예산 부족으로 실패해야 하는 사례를 함께 Dataset에 포함했다.
  * `client.has_dataset()`으로 동일한 이름의 Dataset이 존재하는지 확인하고, 없는 경우에만 새 Dataset을 생성하도록 구현했다.
  * `client.create_dataset()`과 `client.create_examples()`를 이용해 평가 사례를 LangSmith에 등록했다.
  * Dataset을 한 번 생성한 뒤 이후 평가에서는 같은 사례를 재사용하여 baseline과 fixed 버전을 동일한 조건으로 비교할 수 있도록 했다.
  * 코드 수정 전후에 평가 입력이 달라지면 결과를 공정하게 비교할 수 없으므로 공통 Dataset이 필요하다는 점을 이해했다.

  </br></br>

* **Workflow 평가 기준 설계**

  * 단순히 Validator의 PASS/FAIL만 비교하지 않고 결과의 구체적인 내용까지 확인하는 Evaluator를 구현했다.
  * 실제 `passed` 값이 Dataset의 `expected_pass` 값과 같은지 먼저 검사했다.
  * PASS 사례에서는 선택된 장소가 존재하고 실패 조건이 없어야 성공으로 판단했다.
  * FAIL 사례에서는 기대한 실패 키워드가 실제 실패 원인에 포함되어 있는지 확인했다.
  * 예산 부족으로 실패해야 하는 사례가 이전 Task 누락 때문에 우연히 실패한 것은 아닌지 추가로 검사했다.
  * 실패 여부만 같다고 평가를 통과시키지 않고 올바른 이유로 실패했는지를 검증해야 한다는 점을 학습했다.
  * Evaluator는 `key`, `score`, `comment`를 반환하여 평가 점수와 판정 근거를 함께 LangSmith에 기록하도록 구성했다. 

  </br></br>

* **Baseline Experiment 실행**

  * 생성된 Dataset을 이용해 수정 전 `baseline_target`을 평가하는 Experiment를 실행했다.
  * `client.evaluate()`에 평가 대상 함수, Dataset 이름, Evaluator, Experiment Prefix를 전달하는 방법을 실습했다.
  * `max_concurrency=1`로 설정하여 평가 사례가 한 번에 하나씩 실행되도록 구성했다.
  * Metadata에 버전과 수업 정보를 추가하여 Experiment의 목적을 구분했다.
  * 동일한 Baseline Experiment가 이미 존재하는지 `list_projects()`로 확인하고, 중복 실행을 방지하도록 구현했다.
  * Dataset의 각 Example에 대해 Workflow를 실행하고 Evaluator가 결과를 판정하는 전체 평가 흐름을 이해했다.

  </br></br>

* **Fixed Experiment 실행과 수정 전후 비교**

  * Baseline Experiment가 존재하는지 확인한 뒤 수정된 `fixed_target`을 평가하도록 구성했다.
  * Baseline 결과가 없는 상태에서 Fixed 평가만 수행하지 못하도록 실행 순서를 제한했다.
  * 동일한 Dataset과 동일한 Evaluator를 사용해 수정 전후 결과를 공정하게 비교했다.
  * Fixed Experiment가 이미 존재하는 경우에는 다시 평가하지 않고 기존 Experiment 이름을 출력했다.
  * LangSmith의 Datasets & Experiments 화면에서 Baseline과 Fixed의 평가 점수를 비교할 수 있도록 Experiment Prefix를 구분했다.
  * 코드 수정이 특정 사례만 해결했는지, 전체 평가 사례에서 실제 성능이 향상되었는지 확인하는 방법을 학습했다.

  </br></br>

* **Tracing과 Evaluation의 차이**

  * Tracing은 한 번의 실행에서 어떤 Node와 Task가 어떤 입력과 출력을 주고받았는지 관찰하는 기능이라는 점을 학습했다.
  * Evaluation은 여러 테스트 사례에 대해 Workflow 결과가 기대 조건을 만족하는지 반복적으로 측정하는 기능이라는 점을 이해했다.
  * Trace는 오류 원인 분석과 실행 경로 확인에 적합하고, Dataset과 Experiment는 수정 전후 품질 비교와 회귀 테스트에 적합하다는 점을 구분했다.
  * Trace에서 문제를 발견하고 코드를 수정한 뒤 같은 Dataset으로 다시 평가하는 흐름이 AI Workflow 개선 과정이라는 점을 이해했다.
  * AI Workflow도 일반 소프트웨어처럼 관찰, 테스트, 수정, 재평가 과정이 필요하다는 점을 학습했다.

</br></br></br>

#### [느낀 내용]

* 이전에는 Workflow의 실행 결과를 터미널에서만 확인했지만, LangSmith를 이용하면 Planner, Executor, Validator와 세부 Task의 입력과 출력을 한 화면에서 추적할 수 있다는 점이 인상적이었다.

* 단순히 최종 답변이 맞는지만 보는 것이 아니라 어떤 Plan이 만들어졌고, 어떤 Task가 실행되었으며, 어느 단계에서 잘못된 결과가 발생했는지를 확인할 수 있어 디버깅에 유용하다고 느꼈다.

* 환경 변수나 API Key 설정을 먼저 검증하고, Key 원문을 출력하지 않도록 처리하는 과정도 외부 서비스를 연동할 때 필요한 기본적인 운영 코드라는 점을 이해했다.

* Baseline과 Fixed를 동일한 Dataset으로 평가하면서 코드 수정이 실제로 결과를 개선했는지 객관적으로 확인할 수 있다는 점이 가장 실용적으로 느껴졌다.

* 단순히 PASS와 FAIL이 일치하는지만 확인하면 잘못된 이유로 실패한 결과도 통과할 수 있기 때문에, 실패 원인까지 Evaluator에서 검사해야 한다는 점이 중요하게 느껴졌다.

* AI 기능은 실행 결과가 매번 복잡한 경로를 거칠 수 있으므로 Trace와 Evaluation을 함께 구성해야 안정적으로 개선할 수 있다고 생각했다.

#### [활용 방안]

* LangSmith를 사용하는 프로젝트에서는 실행 전에 필수 환경 변수와 API 연결 상태를 검사하는 설정 확인 코드를 구성하기

* API Key와 같은 보안 정보는 원문을 출력하지 않고 마스킹하여 설정 여부만 확인하기

* Workflow 전체는 Chain Run으로, 검색·계산·작성과 같은 내부 작업은 Tool Run으로 나누어 Trace 계층을 구성하기

* Workflow 버전과 실행 목적을 Metadata와 Tag로 기록하여 Baseline, Fixed, LLM 버전의 Trace를 구분하기

* 정상 실행, 검증 실패, Runtime Error 사례를 각각 의도적으로 실행하여 LangSmith에서 오류 위치와 실행 경로를 확인하기

* 반복해서 사용할 대표 입력과 기대 결과를 Dataset으로 만들고, 코드 수정 전후에도 같은 Dataset을 사용하기

* Evaluator에서 PASS/FAIL뿐 아니라 선택 결과, 실패 원인, Task 누락 여부까지 검증하기

* Baseline Experiment를 먼저 기록한 뒤 Fixed Experiment를 동일한 조건으로 실행하여 수정 효과를 비교하기

* Trace에서 발견한 문제를 수정하고 Dataset Evaluation으로 회귀 여부를 확인하는 반복 구조를 프로젝트에 적용하기

* 향후 AI Agent 프로젝트에서도 LangSmith를 이용해 실행 관찰, 오류 분석, 평가, 수정 전후 비교가 가능한 개발 환경을 구성하기
