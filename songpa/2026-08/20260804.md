#### [학습 내용]

* **애플리케이션별 Docker Image 생성**

  * Dockerfile을 작성하여 Node.js, Spring Boot, React 프로젝트를 각각 Docker Image로 만드는 방법을 학습했다.
  * 프로젝트 종류에 따라 Base Image, Build 과정, 실행 명령이 달라진다는 점을 이해했다.
  * `FROM`, `WORKDIR`, `COPY`, `RUN`, `CMD` 등의 명령을 이용해 애플리케이션 실행 환경을 정의했다.
  * `docker build`를 통해 Dockerfile을 Image로 생성하고, 생성한 Image를 Container로 실행하는 과정을 실습했다.
  * 애플리케이션 소스뿐 아니라 Runtime과 Dependency까지 Image에 포함하여 실행 환경을 일관되게 유지할 수 있다는 점을 이해했다.

  </br></br>

* **Node.js와 Redis 애플리케이션 배포**

  * Node.js 애플리케이션과 Redis를 각각 Container로 실행하고 서로 통신하도록 구성하는 방법을 실습했다.
  * 애플리케이션에서 Redis에 접속할 때 `localhost`가 아니라 Container 또는 Compose의 Service 이름을 사용해야 한다는 점을 이해했다.
  * 애플리케이션과 Redis처럼 역할이 다른 서비스를 별도의 Container로 분리하여 관리하는 구조를 학습했다.
  * 하나의 Container에 여러 프로그램을 모두 넣기보다 서비스별로 Container를 분리하는 방식이 관리와 확장에 유리하다는 점을 이해했다.

  </br></br>

* **Docker Compose를 이용한 다중 Container 관리**

  * Docker Compose를 이용하여 애플리케이션, Redis 등 여러 Container를 하나의 설정 파일로 관리하는 방법을 학습했다.
  * Compose 파일에서 Service, Image, Build, Port, Environment, Volume 등의 설정을 정의하는 방법을 익혔다.
  * `docker compose up`과 `docker compose down`을 이용하여 여러 Container를 한 번에 생성하고 종료하는 방법을 실습했다.
  * Compose 내부에서는 Service 이름이 Container 사이의 Host Name처럼 사용된다는 점을 이해했다.
  * 여러 개발자가 동일한 Compose 파일을 사용하면 복잡한 실행 환경을 같은 설정으로 재현할 수 있다는 점을 학습했다.

  </br></br>

* **Volume과 Container 변경 사항 관리**

  * Container 내부에만 저장된 데이터는 Container 삭제 시 사라질 수 있으므로, 보존이 필요한 데이터는 Volume으로 분리해야 한다는 점을 학습했다.
  * Redis나 Database처럼 상태를 유지해야 하는 서비스에 Volume을 적용하는 방법을 익혔다.
  * Host의 파일이나 디렉터리를 Container와 연결하여 변경 사항을 바로 반영하는 Bind Mount 방식을 학습했다.
  * 실행 중인 Container 내부를 직접 수정하면 해당 Container에만 변경 사항이 남아 재현하기 어렵다는 점을 이해했다.
  * 반복해서 사용할 변경 사항은 Dockerfile, Compose 파일 또는 Volume 설정에 반영해야 한다는 점을 학습했다.

  </br></br>

* **Spring Boot 프로젝트 Docker Image 생성**

  * Spring Boot 프로젝트를 Build하여 생성된 JAR 파일을 Docker Image에 포함하는 방법을 실습했다.
  * JDK가 포함된 Image와 실행에 필요한 JRE 중심 Image의 역할을 구분했다.
  * Dockerfile에서 JAR 파일을 복사하고 `java -jar` 명령으로 애플리케이션을 실행하도록 구성했다.
  * Spring Boot 애플리케이션이 사용하는 Port를 Container Port와 연결하여 외부에서 접근하는 방법을 익혔다.
  * Spring Boot 실행에 필요한 환경 변수나 설정값을 Image 내부에 고정하지 않고 실행 환경에서 전달할 수 있다는 점을 이해했다.

  </br></br>

* **React 프로젝트 Docker Image 생성**

  * React 프로젝트를 Build한 뒤 생성된 정적 파일을 웹 서버를 통해 제공하는 Docker Image 구성 방법을 학습했다.
  * React 개발 서버를 그대로 운영 환경에서 사용하는 것이 아니라 Build 결과물을 Nginx와 같은 웹 서버에서 제공하는 구조를 이해했다.
  * Build 단계와 실행 단계를 분리하는 Multi-stage Build 방식을 통해 최종 Image 크기를 줄일 수 있다는 점을 학습했다.
  * React에서 사용하는 API 주소는 Build 시점과 실행 시점의 환경 설정 차이를 고려해야 한다는 점을 이해했다.

  </br></br>

* **클라우드 서버와 가상화**

  * 클라우드 서버는 인터넷을 통해 CPU, Memory, Storage 등의 컴퓨팅 자원을 필요한 만큼 대여하여 사용하는 가상 서버라는 점을 학습했다.
  * 물리 서버를 직접 구매하지 않고 필요한 시점에 생성하며, 사용한 Resource에 따라 비용을 지불하는 구조를 이해했다.
  * Hypervisor는 하나의 물리적 Hardware 위에서 여러 Virtual Machine을 생성하고 관리하는 Software 계층이라는 점을 학습했다.
  * Hardware에 직접 설치되는 Type 1 Hypervisor와 Host 운영체제 위에서 실행되는 Type 2 Hypervisor의 차이를 이해했다.

  </br></br>

* **클라우드 서비스 모델**

  * 클라우드 서비스를 IaaS, PaaS, SaaS로 구분하여 학습했다.
  * IaaS는 가상 서버, Network, Storage 등의 Infrastructure를 제공하고 사용자가 OS와 애플리케이션을 관리하는 방식이라는 점을 이해했다.
  * PaaS는 Runtime과 Middleware 등의 실행 환경을 제공하여 개발자가 애플리케이션 개발과 배포에 집중할 수 있는 방식이라는 점을 학습했다.
  * SaaS는 사용자가 별도의 설치나 서버 관리 없이 완성된 Software 기능을 이용하는 방식이라는 점을 이해했다.
  * 각 모델은 사용자와 Cloud 제공자가 담당하는 관리 범위에 따라 구분된다는 점을 학습했다.

  </br></br>

* **AWS 주요 서비스**

  * EC2는 AWS에서 가상 서버를 생성하고 운영하는 Compute 서비스이며, 생성된 서버 한 대를 Instance라고 한다는 점을 학습했다.
  * S3는 문서, 이미지, 영상 등의 파일을 Object 형태로 저장하는 Storage 서비스라는 점을 이해했다.
  * VPC는 AWS Resource가 동작할 격리된 가상 Network를 구성하는 서비스라는 점을 학습했다.
  * Route 53은 Domain과 AWS Resource를 연결하는 DNS 서비스라는 점을 이해했다.
  * SQS는 애플리케이션 사이에 Message를 전달하는 관리형 Queue 서비스라는 점을 학습했다.
  * Lambda는 별도의 서버를 직접 관리하지 않고 Code를 실행하는 Serverless 서비스라는 점을 이해했다.
  * ECS는 AWS에서 Container를 운영하는 관리형 서비스이고, EKS는 Kubernetes를 관리형으로 제공하는 서비스라는 점을 학습했다.

  </br></br>

* **IAM 계정과 AWS 보안 설정**

  * IAM은 AWS Resource에 접근할 사용자, Group, Role과 권한을 관리하는 서비스라는 점을 학습했다.
  * 모든 권한을 보유한 Root Account 대신 일반 작업에는 IAM User를 사용하는 것이 안전하다는 점을 이해했다.
  * 사용자에게 필요한 권한만 부여하는 최소 권한 원칙을 학습했다.
  * Google Authenticator를 이용해 MFA를 등록하고 추가 인증 절차를 설정하는 방법을 실습했다.
  * Access Key는 AWS CLI나 외부 애플리케이션에서 사용되므로 소스 코드나 공개 저장소에 노출되지 않도록 관리해야 한다는 점을 이해했다.

  </br></br>

* **Elastic Beanstalk를 이용한 배포 자동화**

  * Elastic Beanstalk는 애플리케이션 배포와 운영에 필요한 AWS Resource를 자동으로 구성하는 관리형 PaaS라는 점을 학습했다.
  * 애플리케이션 Code, JAR 또는 WAR 파일을 업로드하면 서버 환경을 자동으로 Provisioning하고 배포할 수 있다는 점을 이해했다.
  * Application, Application Version, Environment, Environment Configuration, Platform의 역할을 구분했다.
  * Load Balancing, Auto Scaling, Monitoring 등의 운영 기능을 자동으로 구성할 수 있다는 점을 학습했다.
  * 인프라 관리 부담을 줄일 수 있지만 세부 설정의 자유도가 제한되고 자동 확장으로 비용 예측이 어려울 수 있다는 점도 이해했다.

  </br></br>

* **AWS Well-Architected Framework**

  * AWS 환경에서 안정적이고 효율적인 Architecture를 설계하기 위한 Well-Architected Framework를 학습했다.
  * 운영 우수성, 보안, 신뢰성, 성능 효율성, 비용 최적화, 지속 가능성의 여섯 가지 기준을 이해했다.
  * Cloud Resource를 생성하는 것에서 끝나는 것이 아니라 운영, 장애 대응, 보안, 성능, 비용을 함께 고려해야 한다는 점을 학습했다.

</br></br></br>

#### [느낀 내용]

* Docker의 기본 개념에서 더 나아가 실제 Node.js, Spring Boot, React 프로젝트를 Image로 만드는 과정을 실습하면서 기술이 배포 과정에서 어떻게 사용되는지 구체적으로 이해할 수 있었다.

* Docker Compose를 사용하면 애플리케이션과 Redis처럼 여러 서비스를 각각 실행하지 않고 하나의 설정으로 관리할 수 있어 개발 환경 구성에 유용하다고 느꼈다.

* 실행 중인 Container를 직접 수정하는 것보다 Dockerfile과 Compose 설정을 변경해야 동일한 환경을 다시 만들 수 있다는 점에서 재현 가능한 환경 구성의 중요성을 알게 되었다.

* Docker는 애플리케이션 실행 환경을 표준화하고, AWS는 해당 애플리케이션이 실행될 서버와 운영 환경을 제공한다는 점에서 두 기술의 연결 관계를 이해할 수 있었다.

* AWS에는 EC2처럼 직접 서버를 관리하는 방식과 Elastic Beanstalk처럼 배포 및 운영을 자동화하는 방식이 있어 프로젝트 요구사항에 맞는 선택이 필요하다고 느꼈다.

* IAM과 MFA 실습을 통해 Cloud 환경에서는 서버 생성보다 계정과 권한을 안전하게 관리하는 것이 우선되어야 한다는 점을 확인했다.

#### [활용 방안]

* Node.js, Spring Boot, React 프로젝트에 각각 적합한 Dockerfile을 작성하여 실행 환경 표준화하기

* 애플리케이션과 Redis, Database 등 여러 서비스를 Docker Compose로 구성하여 한 번의 명령으로 개발 환경 실행하기

* Redis와 Database처럼 보존이 필요한 데이터에는 Volume을 적용하고, 소스 코드 변경이 필요한 개발 환경에는 Bind Mount 활용하기

* Container 내부를 직접 수정하지 않고 Dockerfile과 Compose 설정을 변경하여 동일한 환경을 다시 생성할 수 있도록 관리하기

* React는 Build 결과물을 Nginx에서 제공하고, Spring Boot는 JAR 파일을 실행하는 형태로 운영용 Image 구성하기

* AWS에서는 Root Account 대신 IAM User를 사용하고 MFA와 최소 권한 원칙 적용하기

* Docker로 만든 애플리케이션을 EC2 또는 Elastic Beanstalk에 배포하여 Container 제작부터 Cloud 배포까지 전체 흐름 실습하기

* 서비스 규모와 운영 환경에 따라 직접 EC2를 관리할지, Elastic Beanstalk·ECS·EKS 등의 관리형 서비스를 사용할지 비교하기

* AWS Resource 생성 시 Well-Architected Framework의 보안, 신뢰성, 성능, 비용 기준을 함께 검토하기
