#### [학습 내용]

* **LangGraph vs LangChain 선택**

  * 사용자 투자성향 기반 종목 추천 파이프라인을 설계하며 LangChain과 LangGraph 중 무엇을 쓸지 검토했다.
  * LangChain은 `A → B → C` 방향의 선형 체인에 최적화된 구조라, 밸리데이션 실패 시 재시도하는 사이클을 표현하려면 체인 바깥에서 별도로 루프를 관리해야 한다는 점을 이해했다.
  * LangGraph는 State를 명시적인 TypedDict로 선언하고, 노드 간에 이 State를 공유·누적하며, `add_conditional_edges`로 조건 분기와 사이클을 자연스럽게 표현할 수 있다는 점을 학습했다.
  * 선택 기준은 "재시도 루프 하나" 때문이 아니라 (1) 재시도 사이클 (2) 리스크 성향별 조건 분기 (3) 여러 노드가 공유하는 State, 이 세 가지가 함께 필요해서라는 점을 정리했다.
  * LangGraph의 초기 구축은 State 스키마 정의 등 보일러플레이트가 LangChain보다 다소 번거롭지만, 노드 함수(입력 State → 출력 State) 자체는 난이도가 높지 않고, 오히려 State라는 명시적 계약 덕분에 여러 명이 노드 단위로 나눠 작업하기 쉬운 구조라는 점을 이해했다.

  </br></br>

* **하이브리드 검색 (벡터 + 키워드) 설계**

  * 한국어는 형태소 분석 이슈가 있어, 종목명·종목코드 같은 정확한 키워드 검색에는 pg_trgm(트라이그램) 인덱스가 강하다는 점을 학습했다.
  * "저평가된 안정적인 회사" 같은 의미 기반 질의에는 pgvector 기반 벡터 유사도 검색이 강하다는 점을 이해했다.
  * 별도 벡터DB(Pinecone, Milvus 등)를 추가하지 않고, 이미 사용 중인 PostgreSQL에 pgvector·pg_trgm 확장만 추가해 하이브리드 검색을 구현할 수 있다는 점을 학습했다.
  * 벡터 검색 순위와 키워드 검색 순위처럼 스케일이 다른 두 점수를 그대로 더하면 한쪽이 항상 유리해지는 왜곡이 생기므로, RRF(Reciprocal Rank Fusion)로 순위(rank) 기준으로만 融합해야 공정하다는 점을 이해했다.
  * RRF 공식 `Σ 1/(k+rank)`에서 k값이 클수록 순위 변동에 둔감해지고, k=60은 정보검색 분야의 관례적 기본값이라는 것과, 이는 우리 데이터로 검증된 값이 아니라 "일단 시작하는 값"이라는 점을 학습했다.

#### [느낀 내용]

* 기술 선택(LangGraph vs LangChain, pgvector vs 별도 벡터DB)의 근거를 "어떤 게 더 트렌디한가"가 아니라 "우리 요구사항의 어떤 특성(사이클, 조건분기, 공유 상태) 때문에 필요한가"로 설명할 수 있어야 실제로 설득력 있는 설계가 된다는 걸 느꼈다.
