* 단원명 : LLM 프로젝트
* 학습 주제 : LangGraph, RAG, 하이브리드 검색, 마이크로서비스 아키텍처

#### [학습 내용]

* **순수함수 기반 스코어링 설계**

  * fit_score를 LLM이나 DB 의존성 없는 순수함수로 설계하면 단위테스트가 쉬워지고, 오케스트레이션(LangGraph)과 비즈니스 로직을 분리할 수 있다는 점을 학습했다.
  * fit_score 하나만 반환하면 "왜 이 점수인지" 설명할 수 없기 때문에, score_breakdown(항목별 세부 점수)과 improvement_points(개선포인트 태그)를 함께 반환하도록 설계했다.
  * improvement_tags는 LLM이 생성하는 것이 아니라, 코드에 하드코딩된 topic_map을 기준으로 점수가 0.5 미만인 항목을 규칙 기반으로 추출하는 것이라는 점을 명확히 했다. 이유는 (1) 결정론적이어야 신뢰 가능하고 (2) 태그 종류를 우리가 통제해야 다른 서비스와 협의가 가능하기 때문이다.
  * 실제 가용 데이터(Stock Service 조사 결과)에 맞춰 스코어링 지표를 배당/변동성/밸류에이션 3축에서 밸류에이션(PER·PBR)/수익성(ROE)/변동성 3축으로 재설계했다.

  </br></br>

* **종목 데이터 소유권과 기존 시스템 조사의 중요성**

  * 새 서비스를 설계할 때 "필요한 데이터를 직접 수집"하기 전에, 이미 존재하는 서비스(Stock Service)가 그 데이터를 갖고 있는지부터 확인해야 한다는 점을 체감했다.
  * Stock Service가 종목 마스터·재무정보(stock_financials)·일봉(candles) 데이터를 gRPC로 제공하고 있어, insight 서비스는 원본을 다시 수집하지 않고 필요한 필드만 로컬 stocks_cache로 동기화하면 된다는 구조로 설계를 전환했다.
  * 실제 코드를 점검해보니 PER/PBR/ROE는 스키마상 존재하나 정기 최신화 로직이 구현되어 있지 않아 최신값이 아닐 수 있고, 배당수익률·부채비율은 필드 자체가 없다는 걸 확인했다.
  * "일단 있다고 가정하고 설계"하는 것과 "실제로 조사해서 확인한 뒤 설계"하는 것의 차이를 명확히 느꼈다. 조사 없이 설계했다면 나중에 스키마를 통째로 갈아엎어야 했을 것이다.
  * 부채비율·배당수익률처럼 증권사 API(키움)에 없는 지표는 DART(전자공시) Open API 같은 별도 외부 데이터 소스가 필요할 수 있다는 것과, 이런 지표는 재무제표 갱신 주기(분기)에 따라 달라지는 것과 매일 바뀌는 시세(배당수익률의 분모)가 섞여 있어 갱신 전략을 다르게 가져가야 한다는 점을 학습했다.

  </br></br>

* **캐싱 전략 : Redis/TimescaleDB 대신 PostgreSQL**

  * pg_trgm 인덱스는 PostgreSQL 컬럼에만 걸 수 있어, 종목 캐시를 Redis에 두면 키워드 검색 자체가 불가능하다는 점을 이해했다.
  * 벡터 검색과 키워드 검색이 SQL JOIN으로 처리되는 구조라, 캐시를 다른 저장소로 분리하면 애플리케이션 레벨에서 여러 번 왕복 후 merge해야 해 불필요하게 복잡해진다는 점을 학습했다.
  * TimescaleDB는 직접 가격 시계열을 쌓고 계산할 때 필요한데, 변동성 계산에 필요한 candles 원본은 이미 다른 서비스가 갖고 있어 insight 서비스가 별도 시계열DB를 둘 필요가 없다는 결론을 내렸다.
  * "인프라를 늘리는 것"이 항상 정답이 아니라, 이미 있는 인프라(PostgreSQL)로 요구사항을 충족할 수 있는지 먼저 검토하는 접근을 학습했다.

  </br></br>

* **서비스 간 통신 : 내부는 gRPC, 외부(BFF)는 REST**

  * Candle 컨벤션상 내부 서비스 간 통신은 gRPC, REST는 웹앱-BFF 구간에서만 사용한다는 점을 확인했다.
  * Java는 protoc 플러그인이 빌드 시점에 자동으로 코드를 생성해주는 반면, Python은 grpcio-tools로 별도 명령을 직접 실행해 _pb2.py / _pb2_grpc.py를 생성해야 하고, 이를 빌드 스크립트에 직접 통합해야 한다는 차이를 학습했다.
  * API 계약(.proto)을 로직 구현 이후가 아니라 최대한 먼저 확정해야, 다른 서비스 개발자가 mock을 떠서 병렬 개발이 가능하다는 점을 이해했다.

  </br></br>

* **개발 환경 표준 (패키지 관리, 임베딩/LLM 모델, 예산)**

  * Poetry는 의존성 그룹·락파일·가상환경을 하나로 묶어주는 성숙한 도구지만, 2026년 기준으로는 uv가 pip·가상환경·Python 버전 관리·락파일까지 처리하며 훨씬 빠른 속도로 신규 프로젝트에 권장되는 추세라는 점을 확인했다.
  * Python 버전은 최신 stable보다 한 단계 아래(N-1)가 라이브러리 호환성 면에서 안전하고, 버전 자체보다 락파일 커밋과 팀 전체 버전 통일이 더 중요하다는 점을 학습했다.
  * 임베딩은 text-embedding-3-small, narrative 생성은 gpt-4o-mini를 기본으로 선택했는데, 개발 예산(약 4달러) 대비 500개 종목 narrative 생성 비용이 약 0.07달러 수준으로 매우 여유롭다는 것을 실제 토큰 단가로 계산해 확인했다.

  </br></br>

* **이슈 기반 협업 프로세스**

  * "구두/카톡으로 전달하지 않고 모든 작업은 GitHub Issue로 발행한다"는 팀 컨벤션에 맞춰, 작업 단계(데이터 동기화 → 인프라 → 검색 → 후처리)별로 이슈를 쪼개 작성했다.
  * 혼자 결정 가능한 범위(순수함수 로직, 오케스트레이션 구조, 기존 시스템 리서치)와 팀 상의가 필요한 범위(API 계약, 동기화 방식, 인프라 접근 권한)를 구분하는 기준을 정리했다.
  * 수평적 조직에서 팀장의 제안을 그대로 따르기보다, 그 사이에 확인한 사실(이미 존재하는 종목 데이터, 담당자가 따로 있는 학습콘텐츠)을 근거로 계획을 업데이트해 제안하는 과정을 연습했다.
  * "승률 리포팅"처럼 시간이 지나야 검증 가능한 지표는 개발 속도의 문제가 아니라 물리적으로 지금 당장 불가능한 항목이라는 점을 구분하고, 대신 나중에 계산 가능하도록 지금 스냅샷 필드만 남겨두는 절충안을 이슈에 반영했다.

</br></br></br>

#### [느낀 내용]

* 스켈레톤을 먼저 짜놓고 나중에 실제 데이터를 조사해보니 가정했던 필드(배당수익률, 부채비율)가 존재하지 않는 걸 알게 됐는데, 설계 초기에 "이 데이터가 실제로 있는가"부터 확인하는 습관이 왜 중요한지 체감했다.

* MVP 범위를 정할 때 "시간이 없어서 못 하는 것"과 "시간이 아무리 많아도 지금은 할 수 없는 것"(재학습 루프, 승률 리포팅처럼 실제 시간이 흘러야 검증 가능한 것)을 구분하는 게 우선순위 판단에 중요하다는 걸 배웠다.

* improvement_tags처럼 얼핏 LLM이 만들 것 같은 항목도, 실제로는 결정론적 순수함수로 만드는 게 다른 서비스와의 신뢰 가능한 협업에 더 적합하다는 설계 판단이 인상 깊었다.

</br>

#### [활용 방안]

* 스코어링/의사결정 로직은 가능한 한 순수함수로 분리해 단위테스트를 붙이고, LLM은 "판단"이 아니라 "이미 결정된 근거를 서술"하는 역할로 한정하기

* MVP 범위를 정할 때 제외 항목을 "시간 부족" vs "전제 데이터/조건 부재"로 구분해 문서화하고, 후자는 무엇이 갖춰져야 착수 가능한지 사전작업까지 함께 기록하기

* 작업을 GitHub Issue로 발행할 때, 혼자 결정 가능한 범위와 타 서비스/팀 상의가 필요한 범위를 미리 구분해 이슈 단위를 나누기

* 외부 데이터가 필요한 지표(DART API 등)를 검토할 때는 어떤 API/필드가 필요한지, 갱신 주기가 어떻게 되는지까지 미리 조사해 이슈에 근거로 남겨두기
