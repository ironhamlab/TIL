#### [학습 내용]

* **서비스 네이밍을 기존 레포 컨벤션에서 역으로 추론하기**

  * `webapp`, `stock-items-scanner`, `micro-services` 같은 기존 레포 이름들을 분석해, 접두사 없는 소문자-하이픈 네이밍이 팀 컨벤션임을 파악했다.
  * "insight"라는 가칭이 "추천"보다 "분석/리포팅" 뉘앙스에 가깝다는 점을 인지하고, 서비스의 핵심 산출물(추천)을 그대로 드러내는 `advisory-service`로 확정했다.
  * 향후 AI 관련 서비스가 더 생길 가능성을 감안해, Java의 `micro-services` 모노레포에 대응하는 Python 전용 모노레포(`ai-services` 등)로 갈지, 서비스별 개별 레포를 유지할지는 코드가 아니라 레포 전략 자체를 결정하는 문제이므로 팀장과 상의가 필요한 영역으로 분류했다.

  </br></br>

* **Python 버전 선택 — 최신 vs 안정성**

  * grpcio, asyncpg 같은 C 확장 기반 라이브러리는 새 Python 버전에서 wheel 지원이 늦게 따라오는 경우가 많아, 버전 선택 시 이 부분을 실제로 검색해 확인해야 한다는 점을 배웠다.
  * 검증 결과 Python 3.14도 핵심 의존성이 이미 지원하고 있어 사용 가능했지만, 최종적으로는 2년 이상 검증된 3.12.13을 선택했다. "가장 최신"보다 "충분히 검증된 버전"이 실무적으로 더 안전한 선택일 수 있다는 점을 확인했다.
  * `uv python pin`, `.python-version` 파일, `requires-python = "==3.12.*"`처럼 버전을 팀 전체가 동일하게 고정하는 장치가 버전 자체의 최신성보다 더 중요하다는 점을 학습했다.

  </br></br>

* **REST 초안에서 gRPC 구조로 수정**

  * 처음 제시한 디렉토리 구조(`app/api/routes/recommendations.py`)가 FastAPI+REST 전제였는데, 이미 확정했던 "내부 서비스 간 통신은 gRPC" 컨벤션과 어긋난다는 걸 뒤늦게 발견했다.
  * 이전 대화에서 확정한 결정사항을 이후 산출물에 계속 반영하고 있는지 스스로 점검하지 않으면, 이미 합의된 내용과 어긋난 결과물이 나올 수 있다는 걸 체감했다.
  * `grpc_server/servicer.py`, `server.py` 구조로 수정하고, gRPC 서버 부팅과 gRPC 요청 처리를 분리했다.

  </br></br>

* **커밋 메시지와 .gitignore 컨벤션**

  * 구조만 잡고 실제 로직이 없는 커밋은 `chore:` 타입이 적절하다는 걸 확인했다.
  * .gitignore를 OS/에디터/언어 표준 템플릿만으로 구성하면 프로젝트 특유의 위험 요소(protoc 생성 코드, `.env`, 캐시 디렉토리)를 놓칠 수 있다는 점을 배웠다.
  * `uv.lock`처럼 팀 전체가 동일 버전을 쓰게 강제하는 락파일은 어떤 상황에서도 .gitignore에 넣으면 안 된다는 원칙을 다시 확인했다.

  </br></br>

* **DB 스키마를 한글로 재설명하며 구조 재검토**

  * `stocks_cache`, `stock_narratives`, `user_profiles`, `recommendations` 4개 테이블 각각의 존재 이유를 처음부터 다시 설명하는 과정에서, 스키마 설계가 "원본 데이터 소유권"과 "우리 서비스가 실제로 필요한 것"이라는 두 원칙 위에 세워져 있다는 걸 재확인했다.
  * 코드를 짤 때보다, 이미 만든 걸 남에게(또는 스스로에게) 설명할 때 설계의 허점이나 애매한 지점이 더 잘 드러난다는 걸 느꼈다.

</br></br></br>

#### [느낀 내용]

* 네이밍 하나도 "그럴듯한 이름을 짓는 것"이 아니라 기존 레포 컨벤션을 분석해서 역으로 추론하는 작업이라는 걸 알게 됐다. 사소해 보이는 결정도 근거를 만들어두면 나중에 설명하기 훨씬 쉬워진다.

* 이전에 확정한 결정(gRPC only)을 이후 산출물에서 놓쳤던 경험을 통해, 대화가 길어질수록 "지금까지 뭘 정했는지"를 계속 스스로 점검하는 습관이 필요하다는 걸 느꼈다.

* Python 버전처럼 "최신이 항상 좋다"는 직관이 실무에서는 꼭 맞지 않을 수 있다는 걸 다시 확인했다. 검증된 안정성과 최신성 사이의 트레이드오프를 매번 명시적으로 따져봐야 한다.

</br>

#### [활용 방안]

* 새 프로젝트/서비스 이름을 지을 때 기존 네이밍 패턴을 먼저 분석하고, 그 패턴에서 벗어나는 이유가 있는지 검토하기

* 라이브러리·런타임 버전을 정할 때는 "최신"과 "검증된 버전" 중 어느 쪽이 지금 상황에 맞는지 실제 의존성 호환성을 검색해서 판단하기

* 여러 턴에 걸쳐 대화하거나 작업할 때, 이전에 확정한 결정사항 목록을 주기적으로 다시 훑어보고 지금 산출물이 그 결정과 일치하는지 점검하기

* .gitignore, 커밋 메시지 같은 반복 작업도 "프로젝트 고유의 위험 요소가 무엇인지" 먼저 따져보고 표준 템플릿에 추가하기
