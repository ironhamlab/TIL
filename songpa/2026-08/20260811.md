* 단원명 : LLM 프로젝트
* 학습 주제 : advisory-service 헥사고날 아키텍처 전환 및 실제 실행 검증

---

#### [학습 내용]

* **헥사고날 구조 인지하기**

  * domain이 DB/LLM/gRPC를 전혀 모르는 상태(순수함수), application이 포트(인터페이스)에만 의존하는 상태, infrastructure가 그 포트를 구현하는 상태 — 이 세 가지 특징이 이전 스켈레톤에 자연스럽게 있었다는 걸 확인했다.
  * 헥사고날 구조를 "완벽하게 지키는 것" 자체가 목적이 아니라, 테스트 용이성과 어댑터 교체 유연성이라는 실용적 이유로 유지하는 게 맞다는 결론을 내렸다.

  </br></br>

* **계층별로 코드를 채우는 순서 설계**

  * 외부 의존성이 없는 안쪽 계층(domain)부터 시작해, 포트 인터페이스(application/ports) → 오케스트레이션(application/advisory) → infrastructure 구현체 순으로 진행하면, 막힘없이 갈 수 있는 지점과 외부 조사·협의가 필요해 멈추는 지점을 명확히 구분할 수 있다는 걸 배웠다.
  * "Stock Service의 실제 gRPC 인터페이스"처럼 아직 확정 안 된 의존성은 Protocol로 인터페이스만 먼저 정의해두면, 그 부분이 막혀도 나머지 레이어 개발이 멈추지 않는다는 걸 실제로 적용해봤다.

  </br></br>

* **실제로 돌려봐야만 잡히는 버그**

  * LangGraph 노드를 `lambda s: some_async_fn(s, dep)` 형태로 감쌌더니, LangGraph가 `inspect.iscoroutinefunction`으로 비동기 여부를 판단하지 못해 coroutine을 await하지 않고 그대로 반환값 취급하는 버그가 실제 테스트 실행 중에 발견됐다.
  * `functools.partial`로 바꾸면 원본 async 함수의 시그니처가 유지되어 문제가 해결된다는 걸 확인했다.
  * 코드 리뷰나 정적 분석만으로는 안 잡히고, `uv sync` → `pytest` 실행까지 실제로 거쳐야만 드러나는 버그가 있다는 걸 체감했다. 이후 모든 변경에 대해 "일단 실행해서 확인"하는 습관을 세웠다.

  </br></br>

* **의존성 주입(Composition Root) 패턴**

  * `bootstrap.py` 하나만 infrastructure 구현체의 구체 타입을 알고, domain/application은 포트 인터페이스만 참조하는 구조를 실제로 조립해봤다.
  * gRPC 요청이 들어오면 `transport → bootstrap이 조립한 graph 실행 → domain 계산 → infrastructure가 외부 연동 처리 → transport가 응답 변환`으로 흐르는 전체 그림을 코드 레벨에서 확인했다.

  </br></br>

* **전체 구조를 트리와 함께 다시 설명하기**

  * 59개 파일로 늘어난 구조를 다시 트리 형식으로 정리하고 파일별 역할을 한 줄씩 요약하면서, 스스로도 전체 그림을 다시 점검하는 기회가 됐다.
  * 문서화(README, 트리 요약)가 코드를 다 짠 뒤의 부수 작업이 아니라, 구조 자체가 맞는지 재검증하는 도구로도 쓰일 수 있다는 걸 느꼈다.

</br></br></br>

#### [느낀 내용]

* "이 아키텍처를 꼭 써야 하는가"라는 질문에 대해, 원칙을 무조건 따르기보다 지금 상황에 어떤 이득과 비용이 있는지 따져보고 판단하는 과정이 유익했다. 그 결과 오버엔지니어링이 아니라 실용적 선택이라는 확신을 갖고 진행할 수 있었다.

* 코드를 눈으로만 검토하는 것과 실제로 실행해서 검증하는 것 사이에 생각보다 큰 차이가 있다는 걸 다시 느꼈다. 특히 async/await처럼 런타임에만 드러나는 문제는 실행 없이는 절대 못 잡는다.

* 계층을 나누는 작업 자체보다, "이 계층은 이 계층을 몰라야 한다"는 의존성 방향 규칙을 지키는 게 실제 설계의 핵심이라는 걸 체감했다.

</br>

#### [활용 방안]

* 새로운 아키텍처 패턴을 적용하기 전에, 지금 이미 짠 코드가 그 패턴의 특징을 얼마나 만족하고 있는지 먼저 점검하고 "왜 이 구조가 필요한지"를 실용적 근거로 정리해두기

* 외부 의존성이 확정되지 않은 부분은 Protocol/인터페이스로 먼저 분리해서, 막힌 부분과 진행 가능한 부분을 구분해 병렬로 작업 순서를 짜기

* 코드를 수정한 뒤에는 정적 검토로 끝내지 않고 실제로 테스트를 돌려서 런타임에만 드러나는 문제(특히 async 관련)를 확인하는 습관 유지하기

* 구조가 커질 때는 트리 요약과 파일별 한 줄 설명을 다시 작성해보면서 전체 설계가 여전히 일관성 있는지 재검증하기
