#### [학습 내용]

* **Java 컨벤션 문서에서 언어 무관 원칙과 언어 종속 규칙 구분하기**

  * 기존 Java/Spring 마이크로서비스 컨벤션(CONVENTIONS.md, IDEMPOTENCY.md, BFF 문서)을 Python 서비스에 적용할 때, "언어와 무관하게 지켜야 하는 원칙"과 "Java/Spring 문법에 종속된 규칙"을 구분하는 기준을 세웠다.
  * 도메인별 패키지 레이아웃, JPA Entity, `@Transactional` 같은 건 Java 전용이라 그대로 옮길 수 없지만, gRPC only 통신, 멱등성 키 처리, 인터페이스 분리 원칙, 목록 API의 페이징 계약, DB 마이그레이션 파일 네이밍은 언어와 무관하게 적용해야 한다는 걸 정리했다.

  </br></br>

* **인터페이스 분리 원칙 실전 적용**

  * `StockCatalogPort`가 조회(`get_metrics`)와 동기화(`sync_all`)를 한 인터페이스에 섞어놓은 게, "읽기와 쓰기 요구가 다르면 즉시 분리한다"는 컨벤션 위반이라는 걸 발견했다.
  * `StockMetricsReader`(조회 전용)와 `StockCatalogSynchronizer`(동기화 전용)로 분리하면서, 두 인터페이스의 실제 소비자가 다르다는(하나는 스코어링 노드, 하나는 배치 스케줄러) 것도 함께 확인했다. 인터페이스 분리는 "코드가 깔끔해 보여서"가 아니라 "소비자가 실제로 다르기 때문"에 하는 것이라는 원칙을 체감했다.

  </br></br>

* **팀 컨벤션 적용 여부를 임의로 판단하지 않고 이슈로 확인 요청하기**

  * 멱등성 규칙처럼 원 문서의 예시(주문·취소·정정 등)에 명시적으로 포함되지 않은 케이스(추천 결과 저장)에 대해, 확대 해석해서 그냥 적용하기보다 팀에 명시적으로 확인 요청하는 이슈를 먼저 작성했다.
  * 이렇게 하면 "내 마음대로 해석해서 적용/미적용한 것"이 아니라 "판단 근거를 남기고 합의된 것"이 되어, 나중에 설명하기도 쉽고 팀 컨벤션 자체를 다듬는 데도 기여할 수 있다는 걸 배웠다.

  </br></br>

* **pyproject.toml 버전을 실제로 설치해서 검증**

  * langgraph, openai 같은 핵심 의존성이 메이저 버전이 올라간 상태(0.x→1.2, 1.x→2.x)에서, 눈으로 버전 숫자만 보고 넘어가지 않고 실제로 `uv lock` → `uv sync` → 테스트 실행까지 거쳐 API 호환성을 확인했다.
  * 이 과정에서 `project.scripts` 엔트리포인트가 async 함수를 직접 참조해 실제로는 아무 동작도 안 하는 버그를 발견했다. `main()`(동기 wrapper)과 `_amain()`(실제 비동기 로직)으로 분리해야 한다는 걸 배웠다.

  </br></br>

* **Docker 데몬 없이도 Dockerfile을 단계별로 검증하는 방법**

  * `docker build`를 직접 실행할 수 없는 환경에서, Dockerfile의 각 RUN 명령어를 셸에서 동일한 순서로 재현해 단계별로 검증하는 방법을 적용했다.
  * 이 과정에서 실제로 4개의 버그를 발견했다: (1) dev 그룹(`grpcio-tools`)이 빌드 스테이지에서 설치가 안 됨 (2) `uv run`이 프로젝트 자체를 재설치하려다 `src/`가 아직 없어 실패 (3) `README.md`를 안 복사해서 프로젝트 설치 자체가 실패 (4) `protoc`가 생성한 코드의 import가 절대경로라 우리 패키지 트리 안에서 resolve가 안 됨.
  * 특히 (4)는 이전에 이론적으로만 알고 있던 "Python protoc의 알려진 이슈"가 실제로 재현된 사례였다. `__init__.py`를 직접 생성하고 `sed`로 상대 import로 바꾸는 후처리가 필요하다는 걸 실전에서 확인했다.

  </br></br>

* **1차 구현 이슈와 커밋 메시지 작성**

  * 지금까지 진행한 헥사고날 스켈레톤 구현을 하나의 작업 단위 이슈로 정리하면서, "구현 완료 범위"와 "의도적으로 미구현/보류한 범위"를 명확히 나누어 적었다.
  * 검증 완료 항목(단위테스트 통과, Dockerfile 단계별 재현 검증)을 이슈에 구체적으로 남기면, 리뷰어가 무엇을 다시 검증해야 하는지 신뢰할 수 있는 근거가 된다는 걸 배웠다.

</br></br></br>

#### [느낀 내용]

* 기존 팀 컨벤션을 새로운 언어/기술 스택에 적용할 때, "이건 되고 저건 안 된다"를 혼자 판단하기보다 애매한 부분은 이슈로 명시적으로 확인받는 게 훨씬 안전하고 협업에도 도움이 된다는 걸 느꼈다.

* 의존성 버전을 올릴 때 문서나 changelog만 보고 판단하지 않고 실제로 설치·실행까지 해보는 습관이, 이번에도 실제 버그(엔트리포인트)를 잡아냈다. "실행해서 검증"이 하루 이틀 사이에 반복해서 효과를 보인 원칙이 됐다.

* Dockerfile처럼 컨테이너 환경에서만 재현되는 문제도, 실행 환경이 없다고 포기하지 않고 각 단계를 셸에서 순서대로 흉내 내면 상당 부분 미리 잡아낼 수 있다는 걸 배웠다. 도구가 없다고 검증을 포기할 필요는 없었다.
