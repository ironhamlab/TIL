#### [학습 내용]

- **advisory-service의 Python 패키지 구조 결정**

- 단순한 `app/` 구조와 `src/advisory_service/` 구조를 비교하고, `src` 레이아웃을 사용하는 방향으로 결정했다.
- `app`이라는 이름은 범용적이고 다른 모듈과 충돌하거나 역할이 모호해질 수 있지만, `advisory_service`는 패키지의 책임과 서비스 이름이 명확하게 드러난다.
- 최종적으로 `src/advisory_service` 아래에 domain, application, infrastructure, transport 계층을 배치하는 헥사고날 아키텍처 구조를 사용했다.
- `src` 레이아웃은 프로젝트 루트에 있다는 이유만으로 모듈 import가 성공하는 문제를 방지하고, 실제 설치된 패키지와 동일한 조건으로 테스트할 수 있다는 장점이 있다.

  </br></br>

- **gRPC `server`와 `servicer`의 역할 분리**

- `server.py`와 `servicer.py`가 비슷해 보이지만 서로 다른 역할을 담당한다는 것을 정리했다.
- `servicer.py`는 생성된 `AdvisoryServiceServicer`를 구현하고, gRPC 요청을 application use case로 전달한 뒤 결과를 protobuf 응답으로 변환한다.
- `server.py`는 `grpc.aio.server()` 생성, servicer 등록, health check 등록, 포트 바인딩 및 서버 실행을 담당한다.
- `main.py`는 세부 구현을 직접 포함하지 않고 애플리케이션을 조립하고 gRPC 서버를 시작하는 진입점 역할만 담당하도록 구성했다.

  </br></br>

- **Python 3.12.13과 uv 기반 프로젝트 환경 구성**

- Astral의 설치 스크립트를 사용해 `uv`를 설치하고, 설치 경로인 `$HOME/.local/bin`을 현재 셸의 `PATH`에 반영했다.
- `uv python install 3.12.13`과 `uv python pin 3.12.13`을 이용해 팀에서 사용할 Python 패치 버전을 고정했다.
- `.python-version`에는 정확한 실행 버전을 기록하고, `pyproject.toml`과 `uv.lock`을 통해 프로젝트 의존성을 재현 가능하게 관리하는 방식을 익혔다.
- 일반 의존성과 pytest, Ruff, mypy, grpcio-tools 같은 개발 의존성을 구분해 관리하는 이유도 함께 확인했다.

  </br></br>

- **이미 작성된 proto와 DB 스키마의 범위 확인**

- 처음에는 `advisory.proto`와 `db/schema.sql` 작성을 팀원에게 요청할 작업으로 생각했지만, 실제 저장소를 확인한 결과 두 파일 모두 이미 작성돼 있었다.
- `advisory.proto`에는 `GetRecommendations` RPC와 투자 성향, 투자 기간, 선호 섹터, 추천 결과 및 검증 상태 등의 계약이 정의돼 있었다.
- `schema.sql`에는 `stocks_cache`, `stock_narratives`, `user_profiles`, `recommendations` 테이블과 pgvector, pg_trgm 인덱스가 이미 구성돼 있었다.
- 작업을 분배하기 전에 파일의 존재 여부뿐 아니라 실제 내용을 먼저 확인해야 중복 작업을 막을 수 있다는 점을 배웠다.

  </br></br>

- **Stock Service 전체 동기화 호출량 계산**

- 전체 종목을 약 4천 개로 가정했을 때 `SearchStocks(size=100)` 약 40회와 종목별 `GetStock` 약 4천 회가 필요하므로, 초기 전체 동기화 호출량을 약 4,040회로 계산했다.
- 초당 최대 10회로 제한하면 순수 계산상 약 6분 44초가 걸리고, 네트워크 지연과 재시도를 포함하면 약 7~10분 정도로 예상할 수 있다.
- 사용자 추천 요청에서는 동기화된 종목·재무정보를 로컬 DB에서 조회하고, 변동성이 없는 후보에 대해서만 최대 20회의 `GetCandles`를 호출하도록 설계했다.
- 전체 동기화 시간은 임의로 “비업무 시간”이라고 표현하기보다 `22:30 KST`처럼 시간대를 포함해 구체적으로 합의해야 한다는 점을 정리했다.
- Stock Service의 자체 배치가 있다면 그 배치가 완료된 후 일정 간격을 두고 advisory-service 동기화를 실행해야 한다.

#### [느낀 내용]

- 프로젝트 구조를 정할 때 디렉터리 이름만 비교하기보다 각 모듈의 책임, 의존성 방향, 테스트 방식까지 함께 고려해야 한다는 것을 느꼈다.

- 이미 구현된 파일을 확인하지 않고 일반적인 작업 목록부터 제안하면 팀원에게 중복 작업을 요청할 수 있다는 점을 체감했다. 협업 요청을 작성하기 전에 반드시 현재 저장소 상태를 확인해야 한다.

- “하루 한 번 비업무 시간에 실행”처럼 얼핏 구체적으로 보이는 설명도 운영 관점에서는 모호할 수 있었다. 시간대와 실행 시각, 선행 배치와의 관계까지 명시해야 실제 운영 가능한 계획이 된다.

#### [활용 방안]

- Python 서비스는 `src/<package_name>` 구조를 기본으로 사용하고, 범용적인 `app`보다 서비스 이름이 명확한 패키지명을 사용하기

- gRPC 구현 시 요청 처리 로직은 `servicer.py`, 서버 생성과 실행은 `server.py`, 프로세스 진입은 `main.py`로 분리하기

- 팀원에게 작업을 요청하기 전에 `rg --files`와 실제 파일 내용을 확인해 이미 구현된 범위와 미구현 범위를 구분하기

- 외부 서비스 동기화 계획을 작성할 때 호출 횟수, 동시성, 초당 요청 제한, 예상 소요 시간과 실행 시간대를 함께 명시하기

- 배치 실행 시각은 연동 대상 서비스의 데이터 갱신 완료 시간을 확인한 뒤 결정하기
