- 단원명 : LLM 프로젝트
- 학습 주제 : advisory-service 로컬 테스트 데이터 구성 및 Docker Compose 실행 디버깅

#### [학습 내용]

- **테스트 코드 내부 데이터와 DB 시드 데이터의 차이 이해하기**

- 기존 `test_fit_score.py`와 `test_rrf.py`를 확인한 결과, 두 테스트는 필요한 가짜 데이터를 Python 코드 내부에서 직접 생성하고 있었다.
- `test_fit_score.py`는 음수 PER, 낮은 ROE, 고변동성 등의 `StockMetrics`를 직접 만들어 점수 계산 결과를 검증한다.
- `test_rrf.py`는 벡터 검색 결과와 키워드 검색 결과를 리스트로 만들어, 두 목록에서 높은 순위를 받은 종목이 RRF 결과에서도 상위에 배치되는지 확인한다.
- 따라서 이 단위 테스트들만을 위해 별도의 JSON fixture를 만드는 것은 현재 구조에서는 중복 작업에 가깝다는 것을 확인했다.
- 반면 `seed.sql`은 실제 로컬 PostgreSQL에 가짜 데이터를 입력해 repository와 서비스 실행 흐름을 확인하기 위한 데이터라는 차이가 있다.

  </br></br>

- **로컬 개발용 `seed.sql` 작성**

- `db/schema.sql`의 `stocks_cache` 정의에 맞춰 로컬 개발용 `db/seed.sql`을 작성했다.
- 실제 종목과 혼동되지 않도록 종목 코드를 `TEST001`부터 `TEST005`까지 사용했다.
- 정상 저변동성 종목, 음수 PER 적자 종목, 재무지표가 NULL인 종목, 고변동성 종목, 변동성이 아직 계산되지 않은 종목을 각각 구성했다.
- `ON CONFLICT (stock_code) DO UPDATE`를 사용해 `make seed`를 여러 번 실행해도 동일한 테스트 데이터가 중복 삽입되지 않고 갱신되도록 만들었다.
- 현재 `stocks_cache`에 거래량이나 거래대금 컬럼이 없기 때문에 “낮은 유동성 종목”은 시드 데이터로 표현할 수 없다는 점도 확인했다. 스키마가 지원하지 않는 테스트 조건을 임의로 추가하면 안 된다.

  </br></br>

- **Makefile을 통한 시드 데이터 입력 자동화**

- 긴 `docker compose exec` 명령을 매번 입력하지 않도록 Makefile에 `seed` 타깃을 추가했다.
- `make seed`를 실행하면 실행 중인 PostgreSQL 컨테이너에 `db/seed.sql`을 전달하도록 구성했다.
- 실행 결과로 `INSERT 0 5`가 출력돼 테스트 종목 5개가 정상적으로 입력된 것을 확인했다.
- README에도 `make seed` 사용법과 이 데이터가 운영용이 아닌 로컬 테스트 전용이라는 주의사항을 기록했다.

  </br></br>

- **Docker Compose의 `.env` 파일 문제 해결**

- 첫 번째 `docker compose up --build` 실행에서 `.env` 파일이 없어 Compose가 시작되지 않는 문제를 확인했다.
- `.env.example`을 `.env`로 복사한 뒤 필요한 환경변수를 설정했다.
- Docker 컨테이너 내부의 `localhost`는 PostgreSQL 컨테이너가 아니라 현재 advisory-service 컨테이너 자신을 의미한다는 점을 확인했다.
- 따라서 `DATABASE_URL`의 호스트를 `localhost`가 아닌 Docker Compose 서비스명인 `postgres`로 변경했다.

```env
DATABASE_URL=postgresql://advisory:advisory@postgres:5432/advisory
```

- 아직 Stock Service를 함께 실행하지 않는 로컬 환경에서는 시작 직후 동기화 실패를 방지하기 위해 `STOCK_SYNC_ENABLED=false`로 설정했다.
- `.env`에는 API 키가 포함될 수 있으므로 Git에 커밋하지 않고 `.env.example`만 관리해야 한다.

  </br></br>

- **Docker 로그를 단계별로 구분해서 확인하기**

- Docker 이미지가 `26/26 FINISHED`로 빌드됐다고 해서 서비스 실행까지 성공한 것은 아니라는 점을 확인했다.
- 첫 실행에서는 이미지 빌드, PostgreSQL 실행, pgvector·pg_trgm 확장 및 테이블 생성은 성공했지만 advisory-service는 DB 연결 실패로 종료됐다.
- 수정 후에는 `application_bootstrapped` 로그가 출력돼 DB 연결과 애플리케이션 조립까지 성공했지만, gRPC health check 등록 과정에서 다시 종료됐다.
- 빌드 성공, 인프라 실행 성공, 애플리케이션 부팅 성공을 각각 별도로 확인해야 한다는 것을 배웠다.

  </br></br>

- **gRPC HealthServicer의 잘못된 `await` 수정**

- gRPC 서버 부팅 중 다음 오류가 발생했다.

```text
TypeError: object NoneType can't be used in 'await' expression
```

- 원인은 `health.HealthServicer.set()`이 동기 메서드인데 비동기 메서드처럼 `await`한 것이었다.
- 아래 코드에서 `await`를 제거해 health status가 정상 등록되도록 수정했다.

```python
health_servicer.set(
    SERVICE_NAME,
    health_pb2.HealthCheckResponse.SERVING,
)
health_servicer.set(
    "",
    health_pb2.HealthCheckResponse.SERVING,
)
```

- 수정 후 HealthServicer의 반환값과 Ruff 검사를 확인했고, Docker 이미지를 다시 빌드했다.
- 최종적으로 advisory-service와 PostgreSQL 컨테이너가 모두 `Up` 상태이고, gRPC 포트 `50051`과 PostgreSQL 포트 `5432`가 정상 노출되는 것을 확인했다.

  </br></br>

- **Docker 볼륨의 생명주기 이해하기**

- `docker compose down`은 컨테이너와 네트워크를 종료하지만 PostgreSQL 볼륨은 유지한다.
- `docker compose down -v`는 PostgreSQL 볼륨까지 제거하므로 스키마와 입력한 시드 데이터도 함께 삭제된다.
- 단순 재시작이나 코드 수정 후 재빌드에는 `-v`를 사용할 필요가 없고, DB를 완전히 초기화해야 할 때만 사용해야 한다.

</br></br></br>

#### [느낀 내용]

- 테스트 데이터는 많을수록 좋은 것이 아니라, 어떤 계층과 동작을 검증하려는지에 따라 형태가 달라져야 한다는 것을 배웠다. 순수함수 단위 테스트에는 코드 내부 fixture가 적합하고, 실제 DB 연동 확인에는 `seed.sql`이 유용했다.

- Docker 빌드가 성공해도 애플리케이션이 정상 실행된 것은 아니라는 점을 로그를 통해 명확하게 체감했다. `Built`, `Created`, `Up`을 구분하고 traceback과 종료 코드를 끝까지 확인하는 습관이 필요하다.

- 이번 오류들은 환경변수의 호스트명과 동기·비동기 API 사용처럼 작은 차이에서 발생했다. 코드가 문법적으로 맞는 것만으로는 부족하고, 실제 컨테이너 환경에서 실행해봐야 발견할 수 있는 문제가 많다는 것을 느꼈다.

- 오류를 한꺼번에 해결하려 하기보다 DB 연결, 애플리케이션 조립, gRPC 서버 부팅처럼 실행 단계를 나눠 확인하니 원인을 빠르게 좁힐 수 있었다.

</br>

#### [활용 방안]

- 단위 테스트 fixture와 로컬 DB 시드 데이터의 목적을 구분하고, 같은 데이터를 불필요하게 여러 형식으로 중복 관리하지 않기

- `seed.sql`에는 정상 사례뿐 아니라 음수, NULL, 고변동성 등 실제 장애나 정책 분기를 검증할 수 있는 경계 사례를 포함하기

- 반복 실행되는 시드 SQL은 `ON CONFLICT`를 사용해 멱등하게 작성하기

- Docker Compose 환경에서는 서비스 간 연결에 `localhost`가 아니라 Compose 서비스명을 사용하기

- Docker 실행 결과를 확인할 때 이미지 빌드 완료 여부뿐 아니라 `docker compose ps`, 애플리케이션 로그, 컨테이너 종료 코드까지 확인하기

- 비동기 코드에서 외부 라이브러리 메서드를 호출할 때 함수가 실제 coroutine인지 확인하고, 반환값이 없는 동기 함수에 `await`를 붙이지 않기

- DB 데이터를 보존해야 할 때는 `docker compose down`을 사용하고, 완전 초기화가 필요할 때만 `docker compose down -v`를 사용하기
