
- 단원명 : Candle 프로젝트
- 학습 주제 : Advisory Service 아키텍처와 추천 요청 흐름

---

#### [학습 내용]

- **헥사고날 아키텍처의 역할**

- Advisory Service는 `transport`, `application`, `domain`, `infrastructure` 계층으로 구성되어 있다.
- `transport`는 gRPC 요청 검증과 protobuf 변환, `application`은 추천 실행 흐름, `domain`은 점수와 변동성 같은 비즈니스 규칙을 담당한다.
- `infrastructure`는 PostgreSQL, OpenAI, Stock Service gRPC 등 외부 기술을 구현한다.
- `bootstrap.py`는 application의 Port와 infrastructure의 실제 Adapter를 연결하는 Composition Root다.
- 헥사고날 아키텍처는 필수 구조는 아니지만 외부 의존성을 가짜 구현체로 교체해 테스트하거나 기술 구현을 변경하기 쉬워진다.
- 반면 파일과 인터페이스가 많아지고 실행 흐름이 여러 계층에 분산되어 초기 이해 비용이 증가한다.

  </br></br>

- **gRPC 요청에서 Use Case까지의 흐름**

- 추천 요청은 `AdvisoryServicer`가 가장 먼저 받는다.
- Servicer는 metadata의 `x-user-id`와 위험 성향, 투자 기간, 선호 업종, 자유 질의를 검증한다.
- 검증된 protobuf 요청은 내부 도메인 모델인 `InvestorProfile`로 변환된다.
- Servicer는 추천 로직을 직접 실행하지 않고 `GenerateAdvisoryUseCase.execute()`를 호출한다.
- protobuf 객체를 내부 로직에서 직접 사용하지 않기 때문에 gRPC 외에 REST, Batch, CLI 같은 다른 진입점에서도 추천 기능을 재사용할 수 있다.

  </br></br>

- **Use Case와 LangGraph의 역할 구분**

- Use Case는 `application/advisory/use_case.py`의 `GenerateAdvisoryUseCase`다.
- Use Case는 초기 `AdvisoryState` 생성, LangGraph 실행, 최종 검증 상태 판정, 성공 결과 저장과 반환을 담당한다.
- `graph.py`는 다음 실행 순서와 재시도 분기를 정의한다.

```text
build_profile
→ retrieve_candidates
→ score_candidates
→ generate_narrative
→ validate_result
```

- `nodes/*.py`는 각 단계의 실제 작업을 수행하고, `fit_score.py`와 `volatility.py`는 핵심 계산 규칙을 담당한다.
- 검증에 실패하면 전체 과정을 반복하지 않고 narrative 생성 단계만 다시 실행한다.
- 최초 검증 성공은 `PASSED`, 재생성 후 성공은 `RETRIED`, 최종 실패는 `FAILED`로 구분한다.
- 검증을 통과한 결과만 PostgreSQL에 저장한다.

  </br></br>

- **추천 후보가 없을 때의 현재 동작**

- 추천 후보가 없으면 `validate_result`가 `추천 가능한 종목이 없습니다` 오류를 추가한다.
- 현재 Graph는 후보 없음과 narrative 품질 실패를 구분하지 않아, 후보가 없어도 narrative 생성을 다시 실행한다.
- `MAX_RETRY = 2`는 실제 추가 실행 횟수라기보다 검증 실패 횟수다.
- 최초 검증과 재생성 후 검증이 모두 실패하면 화면에 재시도 2회로 표시되지만, 실제 narrative 재생성은 한 번이다.
- 후보가 없는 경우에는 즉시 종료하고, narrative만 잘못된 경우에만 재생성하도록 실패 원인별 분기가 필요하다.

</br></br></br>

#### [느낀 내용]

- 헥사고날 아키텍처는 당장 코드를 짧게 만드는 구조가 아니라 장기적인 테스트와 변경 비용을 낮추기 위한 구조라는 점을 이해했다.

- Use Case, Graph, Node와 Domain Service의 책임을 구분하니 여러 파일로 나뉜 추천 흐름을 이해하기 쉬워졌다.

- 재시도 로직은 단순히 횟수만 정하는 것이 아니라, 실패 원인에 따라 다시 실행해야 할 단계를 구분해야 한다고 느꼈다.

</br>

#### [활용 방안]

- 외부 의존성이 많은 서비스에서는 Port와 Adapter를 이용해 비즈니스 로직과 기술 구현을 분리하기

- 사용자 기능의 시작과 종료는 Use Case, 실행 순서와 분기는 Graph, 핵심 계산은 Domain Service에 배치하기

- 재시도 로직을 설계할 때 후보 부족, 외부 서비스 장애, 생성 결과 오류를 구분해 필요한 단계만 다시 실행하기
