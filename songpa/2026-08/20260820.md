#### [학습 내용]

- **Trading Service의 역할과 요청 흐름**

- Trading Service는 Account, Order, Reservation 세부 도메인으로 구성된다.
- Account는 현금과 잠금 잔액, Order는 시장가·지정가 주문과 체결, Reservation은 예약 주문의 생성과 전환을 담당한다.
- 쓰기 요청이 들어오면 gRPC Interceptor가 `x-user-id`와 `x-idempotency-key`의 형식을 검사하고 Context를 생성한다.
- IdempotencyExecutor가 사용자, RPC operation과 멱등성 키로 기존 처리 기록을 조회하고 요청 Hash를 비교한다.
- 신규 요청이면 비즈니스 로직을 실행하고 도메인 변경, Outbox와 성공 응답을 하나의 트랜잭션으로 저장한다.

  </br></br>

- **비관적 락을 이용한 잔액 정합성**

- 동일 계좌에서 여러 매수 주문이 동시에 같은 가용 잔액을 조회하면 잔액을 초과하는 주문이 모두 승인될 수 있다.
- 잔액 변경 직전에 계좌 행을 비관적 락으로 조회하고, 락을 획득한 요청만 최신 가용 잔액을 검증한다.
- 지정가 매수 주문은 주문 원금과 예상 수수료를 잠금 잔액으로 선점해 다른 주문이 같은 금액을 사용하지 못하게 한다.
- 계좌 잠금, Order 저장, Outbox 이벤트와 멱등성 응답은 동일 트랜잭션으로 처리한다.
- 비관적 락은 동일 계좌의 주문을 직렬화해 처리량을 낮출 수 있지만, 금융성 데이터에서는 잔액 초과 승인 방지를 우선했다.

  </br></br>

- **멱등성을 이용한 중복 주문 방지**

- 주문 처리는 성공했지만 응답이 유실되면 클라이언트가 같은 요청을 다시 전송할 수 있다.
- 동일 키와 동일 요청은 비즈니스 로직을 다시 실행하지 않고 저장된 protobuf 응답을 반환한다.
- 동일 키에 종목·수량·가격이 다른 요청이 들어오면 요청 Hash 불일치로 거절한다.
- 동시 요청은 DB PK 또는 UNIQUE 제약이 하나만 성공시키고, 나머지는 성공한 요청의 응답을 재생한다.
- Interceptor는 metadata 검증과 Context 생성을 담당하고, 실제 DB 조회·Hash 검증·응답 재생은 IdempotencyExecutor가 담당한다.

  </br></br>

- **Transactional Outbox 기반 예약 주문 전환**

- 예약 실행일이 되면 Reservation을 RESERVED에서 CONVERTING으로 변경하고 `ReservationDue` Outbox 이벤트를 같은 트랜잭션에 저장한다.
- 이벤트가 Kafka로 전달되면 Order 영역이 일반 주문을 생성하고 `ReservationConverted` 이벤트를 기록한다.
- Reservation 영역은 해당 이벤트를 소비해 원래 예약을 EXECUTED로 변경한다.
- 상태 변경 후 Kafka를 직접 호출하지 않고 상태와 Outbox를 함께 저장해, DB 반영은 성공했지만 이벤트가 유실되는 부분 실패를 줄인다.
- Publisher는 전송 성공 후 `published_at`을 기록하므로 장애 시 같은 이벤트가 다시 발행될 수 있다.
- Outbox는 exactly-once가 아닌 at-least-once 구조이며, 멱등성 키, 상태 재검증과 UNIQUE 제약으로 중복을 방어한다.

  </br></br>

- **기술 발표 자료 구성**

- 코드 전체 과정을 긴 문단으로 읽는 방식보다 `문제 → 해결 → 결과 → Trade-off`로 나눠 설명하는 편이 효과적이다.
- 프로젝트 전체 설명은 앞부분에서 다루고, 담당 부분은 다음 7개 슬라이드로 압축했다.

```text
1. Trading & Advisory 담당 영역
2. 동시 주문과 비관적 락
3. 멱등성 키와 요청 Hash
4. Outbox 기반 예약 주문 전환
5. Advisory 추천 Workflow
6. Hybrid Search와 정량 점수
7. AI Agent 대신 Workflow를 선택한 이유
```

- 기존 발표 자료에서 Interceptor가 DB를 조회한다는 잘못된 설명을 수정했다.
- 현재 코드에 없는 분산 락 표현을 제거하고 DB PK·UNIQUE 충돌 처리로 변경했다.
- Exactly-once 표현을 `at-least-once + Consumer 멱등성`으로 수정해 실제 코드의 보장 수준과 맞췄다.
- 발표에서는 기술 이름을 나열하기보다 무엇을 포기하고 어떤 특성을 얻었는지 설명해야 한다.

</br></br></br>

#### [느낀 내용]

- 강한 정합성과 최종 일관성은 경쟁 관계가 아니라 적용 범위가 다른 설계 방식이라는 점을 이해했다.

- 사용자 요청과 잔고 변경에는 트랜잭션과 비관적 락을 적용하고, 도메인 간 후속 처리에는 Outbox와 Kafka를 적용하는 이유를 구분할 수 있게 됐다.

- 멱등성과 Outbox를 적용하더라도 중복이 자동으로 사라지는 것은 아니며, DB 제약과 Consumer의 상태 검증이 함께 필요했다.

- 발표에서는 “완벽하게 방지했다”는 표현보다 실제 코드가 제공하는 보장 수준과 Trade-off를 정확히 설명하는 것이 중요하다고 느꼈다.

</br>

#### [활용 방안]

- 금융성 잔액 변경에서는 충돌 가능성과 복구 비용을 고려해 비관적 락 사용 여부 결정하기

- 쓰기 API에 멱등성 키와 요청 Hash를 적용해 동일 요청의 안전한 재전송 지원하기

- DB 상태와 Kafka 이벤트의 원자성이 필요할 때 Transactional Outbox를 사용하고 Consumer 멱등성도 함께 설계하기

- 발표 자료는 한 슬라이드에 하나의 문제와 선택 근거만 배치하기

- `exactly-once`, `분산 락`, `완벽한 유실 방지`처럼 실제 구현보다 강한 표현을 피하고 검증 가능한 수준으로 설명하기
