#### Advisory Service

- **PER·PBR·ROE의 의미와 추천 지표 활용**

- PER는 주가를 주당순이익으로 나눈 값으로, 기업의 이익에 비해 현재 주가가 몇 배로 거래되는지를 나타낸다.
- PBR는 주가를 주당순자산으로 나눈 값으로, 기업의 순자산 대비 주가 수준을 평가하는 지표다.
- ROE는 자기자본 대비 당기순이익의 비율로, 주주의 자본을 이용해 얼마나 효율적으로 이익을 냈는지를 보여준다.
- Advisory Service에서는 PER와 PBR를 밸류에이션 평가에 사용하고, ROE를 수익성 평가에 사용한다.
- 세 지표 모두 낮거나 높다고 무조건 좋은 것은 아니며, 업종 특성이나 기업의 성장성, 부채 수준 등을 함께 고려해야 한다.

  </br></br>

- **밸류에이션·수익성 점수 계산 방식**

- 현재 서비스에서 밸류에이션은 기업의 적정가치를 직접 계산하는 개념보다, PER와 PBR를 이용해 현재 주가의 부담 수준을 평가하는 의미로 사용한다.
- PER 10 이하와 PBR 1 이하를 높은 점수의 기준으로 두고, 값이 커질수록 0~1 범위에서 점수가 선형적으로 감소하도록 구현했다.
- PER 점수와 PBR 점수의 평균을 밸류에이션 점수로 사용하며 최종 적합도에서 35%를 반영한다.
- 수익성 점수는 ROE를 15로 나누어 계산하고, ROE 15% 이상이면 최대 1점으로 제한한다.
- ROE 기반 수익성 점수는 최종 적합도에서 30%를 반영한다.
- 현재 기준값과 가중치는 학습 데이터로 최적화한 결과가 아니라 서비스의 초기 추천 정책값이며, 추후 백테스트와 사용자 데이터를 이용한 조정이 필요하다.

  </br></br>

- **최근 90일 변동성과 위험 성향별 적합도**

- Stock Service에서 완료된 최근 일봉 종가 91개를 조회해 90개의 일간 로그수익률을 계산한다.
- 각 로그수익률의 표준편차에 연간 거래일 수인 252의 제곱근을 곱하고 100을 곱해 연율화 변동성을 구한다.
- 따라서 코드에서 사용하는 90일 변동성은 달력 기준 90일보다 최근 90거래 구간의 가격 변동성에 가깝다.
- 안정형은 0~15%, 중립형은 10~30%, 공격형은 20~100%를 적합한 변동성 범위로 사용한다.
- 종목의 변동성이 해당 범위 안이면 1점을 부여하고, 범위를 벗어나면 가장 가까운 경계와의 거리에 따라 점수를 차감한다.
- 변동성 적합도는 최종 점수에서 35%를 반영한다.
- 변동성은 요청마다 계산하지 않고 미리 계산해 캐시에 저장하며, 기본적으로 24시간 이내의 값은 다시 사용한다.

  </br></br>

- **RRF를 이용한 하이브리드 검색**

- 자연어의 의미가 유사한 종목을 찾는 pgvector 검색과 종목명·종목코드·키워드를 찾는 pg_trgm 검색을 함께 사용한다.
- 두 검색 방식은 유사도 점수의 의미와 범위가 다르기 때문에 원점수를 직접 더하지 않고 RRF로 검색 순위를 결합한다.
- RRF는 각 검색 결과에서 높은 순위에 등장할수록 높은 점수를 주고, 두 검색 결과에 모두 등장한 종목은 점수가 누적된다.
- 현재 구현에서는 `1 / (60 + 순위)`를 검색 결과별로 더해 RRF 점수를 계산한다.
- RRF는 최종 투자 적합도를 결정하는 점수가 아니라, 평가할 후보 종목을 최대 20개까지 선정하는 데 사용한다.
- 최종 상위 5개 종목은 RRF 점수가 아닌 재무지표와 변동성으로 계산한 적합도 점수를 기준으로 선정한다.

  </br></br>

- **순수함수와 단위 테스트 검증**

- 밸류에이션·수익성·변동성 적합도 계산은 DB, gRPC, LLM과 분리된 순수함수로 구현돼 있다.
- 동일한 입력에 동일한 결과를 반환하므로 경곗값과 위험 성향별 결과를 독립적으로 테스트할 수 있다.
- PER가 음수일 때의 점수, ROE 증가에 따른 수익성 점수 변화, ROE 15% 상한, 위험 성향별 변동성 점수와 개선 태그를 테스트했다.
- 변동성 계산에서는 가격이 일정할 때 0을 반환하는지, 종가가 부족할 때 `None`을 반환하는지, 가격이 변할 때 양수의 연율화 변동성이 계산되는지를 검증했다.
- RRF 테스트에서는 두 검색에서 모두 상위에 등장한 종목이 최종 1위가 되는지와 한쪽 검색에만 등장한 종목도 누락되지 않는지를 확인했다.
- Advisory Service의 전체 단위 테스트를 실행한 결과 32개 테스트가 모두 통과했다.

#### Trading Service

- **비관적 락을 이용한 동시 주문 제어**

- 같은 계좌에서 여러 매수 주문이 동시에 들어오면 각 요청이 변경 전 잔액을 읽어 가용 잔액보다 많은 주문이 승인될 수 있다.
- 이를 방지하기 위해 잔액을 검증하고 주문 금액을 선점하기 전에 계좌 행에 `PESSIMISTIC_WRITE` 락을 적용한다.
- 먼저 락을 획득한 요청이 최신 잔액을 확인하고 주문 금액과 예상 수수료를 잠금 잔액으로 선점한다.
- 다음 요청은 앞선 트랜잭션이 끝난 후 변경된 잔액을 확인하므로 잔액을 초과한 주문이 거절된다.
- 테이블 전체가 아니라 특정 계좌 행을 잠그기 때문에 서로 다른 사용자의 주문은 병렬로 처리할 수 있다.
- 동일 계좌 주문이 순차 처리되어 처리량이 감소할 수 있지만, 거래 도메인에서는 처리량보다 잔액 정합성을 우선했다.

  </br></br>

- **주문 접수와 체결의 구분**

- 시장가 주문은 현재가를 조회한 뒤 주문 생성과 체결·정산을 즉시 진행한다.
- 지정가 매수 주문은 지정 가격을 기준으로 주문 금액과 예상 수수료를 먼저 선점하고 `PENDING` 상태로 저장한다.
- 이후 시장 가격이 매수 지정가 이하로 내려가면 체결 조건을 만족한 것으로 판단한다.
- 지정가 매도 주문은 시장 가격이 사용자가 지정한 가격 이상이 되면 체결 조건을 만족한다.
- 실제 체결 시에는 체결 내역을 생성하고 계좌를 정산한 뒤 주문 상태를 `FILLED`로 변경한다.
- 주문이 취소되거나 만료되면 사용하지 않은 잠금 잔액을 다시 가용 잔액으로 반환해야 한다.

  </br></br>

- **멱등성 키와 요청 Hash를 이용한 중복 주문 방지**

- 네트워크 타임아웃이나 사용자의 재시도로 동일한 주문 요청이 여러 번 전달될 수 있다.
- 사용자 ID, RPC 종류와 멱등성 키를 기준으로 이전 처리 기록을 조회해 신규 요청과 재시도를 구분한다.
- 처음 들어온 요청이면 비즈니스 로직을 실행하고 처리 결과인 protobuf 응답을 저장한다.
- 동일 키와 동일 요청이 다시 들어오면 주문을 재실행하지 않고 저장된 응답을 반환한다.
- 같은 멱등성 키에 종목, 수량이나 가격이 다른 요청이 들어올 수 있으므로 요청 본문의 Hash도 함께 비교한다.
- 키는 같지만 Hash가 다르면 정상적인 재시도가 아닌 키 오용으로 판단해 충돌로 거절한다.
- 계좌와 주문, Outbox 이벤트, 멱등성 응답을 하나의 트랜잭션으로 저장해 일부 데이터만 반영되는 상황을 방지한다.

  </br></br>

- **Transactional Outbox와 중복 이벤트 처리**

- 예약 상태를 데이터베이스에서 변경한 뒤 Kafka 발행에 실패하면 예약은 변경됐지만 실제 주문 전환이 누락될 수 있다.
- 이를 방지하기 위해 예약 상태 변경과 Outbox 이벤트를 같은 데이터베이스 트랜잭션에 저장한다.
- 별도의 Publisher가 아직 발행되지 않은 Outbox 이벤트를 조회해 Kafka로 전달한다.
- Publisher가 Kafka 전송 후 발행 상태를 기록하기 전에 중단되면 동일 이벤트가 다시 발행될 수 있다.
- 따라서 Outbox는 이벤트 유실을 방지하는 데 사용하고, 중복 전달은 예약 ID 기반 멱등성 키와 상태 검사, UNIQUE 제약으로 방어한다.
- Kafka의 전달 수준은 `at-least-once`이며, Consumer의 멱등 처리를 통해 비즈니스 결과가 한 번만 반영되도록 구성한다.

  </br></br>

- **주문 상태 전이와 경합 처리**

- 주문 취소와 체결이 동시에 발생할 경우 두 작업 모두 주문 행에 락을 획득한 뒤 최신 상태를 다시 확인해야 한다.
- 먼저 실행된 작업이 `PENDING` 주문을 `FILLED` 또는 `CANCELLED`로 변경하면 나중 작업은 상태 조건을 통과하지 못해 중단된다.
- 같은 가격 이벤트가 Kafka로 반복 전달되더라도 체결 전에 주문 상태를 확인해 이미 `FILLED`인 주문은 다시 처리하지 않는다.
- 조회 시점에 주문이 `PENDING`이었더라도 실제 변경 직전에 다시 상태를 확인해야 동시 처리 과정의 중복 체결을 방지할 수 있다.
- 애플리케이션의 `synchronized`는 여러 서버 인스턴스 사이에서 공유되지 않으므로, 확장 가능한 환경에서는 데이터베이스 락과 제약조건이 필요하다.

#### [느낀 내용]

- 추천 서비스의 수치를 설명할 때 단순히 공식만 외우는 것보다, 각 지표가 기업의 어떤 측면을 평가하는지를 이해해야 질문에 대응할 수 있다는 것을 느꼈다.

- 현재 가중치와 위험 구간이 통계적으로 최적화된 값이 아니라 초기 정책값이라는 사실을 명확하게 설명하는 것이 중요했다. 구현의 한계를 숨기기보다 개선 방향과 함께 제시하는 편이 설계 의도를 더 정확하게 전달할 수 있다.

- AI가 검색 후보와 설명 생성에는 참여하지만 최종 점수는 순수함수로 계산한다는 역할 분리가 Advisory Service의 핵심 설계라는 점을 다시 정리할 수 있었다.

- 금융 서비스에서는 정상 흐름보다 동일 요청이 반복되거나 여러 작업이 동시에 실행되는 예외 상황을 먼저 고려해야 한다는 점을 느꼈다.

- 비관적 락, 멱등성, Outbox는 각각 독립적인 기술이 아니라 잔액 초과 승인, 중복 주문, 이벤트 유실처럼 서로 다른 실패 상황을 해결하기 위한 장치라는 것을 이해했다.

- Outbox를 적용했다고 해서 중복 이벤트까지 사라지는 것은 아니며, Producer의 유실 방지와 Consumer의 중복 방어가 함께 구성돼야 한다는 점을 알게 됐다.

#### [활용 방안]

- 추천 지표를 설명할 때 `지표의 의미 → 코드의 계산 방식 → 현재 한계` 순서로 답변하기

- RRF 점수는 후보 검색용이고 적합도 점수는 최종 순위 결정용이라는 차이를 명확하게 구분하기

- 가중치와 기준값을 설명할 때 검증된 최적값이라고 과장하지 않고 초기 정책값이라고 표현하기

- 업종별 상대평가와 백테스트, 사용자 선택 데이터를 이용한 가중치 튜닝을 향후 개선 과제로 제시하기

- 테스트 여부를 질문받으면 순수함수 테스트, Workflow 테스트와 실제 테스트 통과 결과를 함께 설명하기

- Trading Service를 설명할 때 기술 이름보다 `어떤 실패 상황을 막기 위해 적용했는지`를 먼저 설명하기

- 동시 주문 질문에는 계좌 행 락, 최신 잔액 재검증, 잠금 잔액 선점과 트레이드오프를 함께 답변하기

- 멱등성 질문에는 동일 키·동일 요청과 동일 키·다른 요청의 처리 차이를 구분해 설명하기

- Kafka의 중복 전달을 전제로 상태 검사, 멱등성 키와 UNIQUE 제약을 함께 적용하기

- 주문 취소·체결처럼 상태 변경이 경합하는 작업은 실제 변경 직전에 최신 상태를 다시 검증하기
