
- 단원명 : ICT CoC 현장실습 및 프로젝트
- 학습 주제 : Todo 프로젝트 Entity/Repository 설계

---

#### [학습 내용]

* JPA Entity 애노테이션의 역할
  - `@Entity`는 "이 클래스가 테이블과 매핑된다"는 표시일 뿐, 실제 동작은 Hibernate가 담당한다.
  - `@Id` + `@GeneratedValue(strategy = GenerationType.IDENTITY)`로 PK를 DB의 AUTO_INCREMENT에 위임한다. `AUTO`보다 명시적으로 `IDENTITY`를 지정하는 게 예측 가능성과 최적화 여지 측면에서 유리하다.
  - `nullable = false`는 필수 필드에만 선택적으로 붙이면 되고, `@Id` 필드는 PK 정의상 이미 null 불가라 별도 지정이 불필요하다.

* 연관관계는 단방향(자식→부모)만
  - `Todo`(자식)에는 `@ManyToOne` + `@JoinColumn(name = "user_id")`으로 `User`를 참조하되, `User`(부모)에는 `@OneToMany`를 걸지 않는다.
  - 양방향 연관관계는 무한루프(StackOverflowError)나 LazyInitializationException의 원인이 될 수 있어, 필요한 조회는 Repository의 커스텀 메서드(`findAllByUserId` 등)로 해결한다.
  - `@ManyToOne` 필드명은 실제 타입(`User`)을 반영해 `user`로 짓는다 — `userId`라고 지으면 필드에 값(Long)이 아니라 객체가 들어있다는 사실과 이름이 어긋난다.

* Enum을 DB에는 문자열로 저장하기
  - `@Enumerated(EnumType.STRING)`을 쓰면 자바에서는 enum 타입(`TodoStatus.TODO`)으로 다루면서 DB에는 VARCHAR로 저장된다.
  - `EnumType.ORDINAL`(순서를 숫자로 저장)은 저장 공간이 작다는 장점이 있지만, enum 순서 변경 시 기존 데이터 의미가 깨지는 위험이 커서 실무에서는 `STRING`이 표준적으로 선호된다.

* JPA 생성자 설계 원칙
  - `@NoArgsConstructor`(JPA 필수 요구사항)와, 실제 생성 시 필요한 필드만 받는 커스텀 생성자를 분리한다.
  - `@AllArgsConstructor`는 자동 생성 필드(`id`, `createdAt` 등)까지 파라미터로 받게 돼 오히려 불편하므로 지양한다.
  - Setter는 클래스 전체에 열어두지 않고, 상태 변경이 필요한 시점에 의도가 담긴 전용 메서드(`updateStatus()` 등)를 만드는 방식을 추천받았다.

* Repository는 인터페이스 선언만으로 동작
  - `JpaRepository<Entity, PK타입>`을 상속하면 `findById`, `save`, `findAll`, `deleteById` 등이 기본 제공되며, 구현체는 Spring Data JPA가 런타임에 프록시로 자동 생성한다.

#### [느낀 내용]

- JPA 애노테이션 하나하나가 "왜 이렇게 써야 하는지" 이유를 알고 나니, 단순 암기가 아니라 설계 판단으로 이해되기 시작했다.
- 양방향 연관관계를 안 쓰는 이유가 PayFor에서 이미 원칙으로 정해둔 것과 동일한 이유(무한루프, LazyInitializationException)라서, 두 프로젝트의 학습이 서로 강화되는 느낌을 받았다.

</br></br>

#### [활용 방안]

- 새 Entity를 만들 때마다 "이 필드가 필수인가"를 먼저 판단하고 nullable을 선택적으로 붙이는 습관 들이기
- 연관관계 설계 시 항상 자식→부모 단방향만 걸고, 반대 방향 조회가 필요하면 Repository 커스텀 메서드로 해결하기
- 상태값이 제한된 선택지를 가지면 String이 아니라 Enum + `@Enumerated(EnumType.STRING)`으로 설계하기
