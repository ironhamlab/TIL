- 학습 주제 : DTO 설계와 Docker/MySQL 환경 트러블슈팅

---

#### [학습 내용]

* DTO를 쓰는 이유와 record 문법
  - Entity를 그대로 API 응답으로 내보내면 연관관계 직렬화 문제(Lazy Loading), 불필요한 필드 노출, 계층 간 책임 혼재 문제가 생긴다.
  - Java `record`는 필드 선언(생성자, Getter, equals/hashCode/toString)을 한 줄로 자동 생성해주는 문법이며, Getter 호출은 `getXxx()`가 아니라 `xxx()` 형태다.
  - 요청 DTO에는 클라이언트가 실제로 보내야 하는 값만 담고(Entity 참조 대신 `Long userId`처럼 ID값만), 응답 DTO에는 클라이언트에게 보여줄 필드만 선별해서 담는다.

* Docker MySQL 트러블슈팅 — 여러 원인이 겹칠 수 있음을 경험
  - `Access denied` 에러가 계정 자체보다 로컬에 이미 떠 있는 MySQL(brew 서비스)이 같은 포트(3306)를 선점해서 발생할 수 있다.
  - `lsof -i :3306`으로 포트 점유 프로세스를 확인하고, `caching_sha2_password`를 `mysql_native_password`로 바꾸거나 포트를 분리(`3307:3306`)해서 해결한다.
  - `docker-compose.yml`의 `MYSQL_USER`/`MYSQL_PASSWORD` 환경변수는 볼륨이 비어있는 최초 생성 시에만 적용되므로, 설정을 바꿨다면 `docker compose down -v`로 볼륨까지 초기화해야 반영된다.

* `application.yml`과 `ddl-auto` 옵션
  - `ddl-auto`는 `none`/`validate`/`update`/`create`/`create-drop` 5가지가 존재하며(`create-update`는 존재하지 않는 값), 개발 중에는 `update`가 적합하다.
  - `show-sql: true`로 Hibernate가 실제로 생성하는 SQL을 콘솔에서 직접 확인할 수 있다.

#### [느낀 내용]

- 에러 메시지 하나(`Access denied`)가 계정 문제처럼 보여도 실제로는 인프라 레벨(포트 충돌)의 문제일 수 있다는 걸 직접 겪으며 배웠다. 증상만 보고 성급하게 원인을 특정하지 않고 단계적으로 좁혀가는 디버깅 과정이 체감됐다.
- Django ORM과 비교했을 때 JPA/Spring이 계층을 훨씬 엄격하게 나누는 이유가, 생산성보다 "커질수록 안 무너지는 구조"를 우선하는 설계 철학 차이에서 온다는 걸 이해했다.

</br></br>

#### [활용 방안]

- DB 연결 에러가 나면 계정/비밀번호보다 먼저 포트 점유 여부(`lsof`)부터 확인하는 순서로 디버깅하기
- DTO 설계 시 "클라이언트가 실제로 보내는/받아야 하는 값이 뭔지"부터 정하고 필드를 구성하기
- docker-compose 설정을 바꿨는데 반영이 안 되면 볼륨 초기화(`down -v`)부터 의심하기
