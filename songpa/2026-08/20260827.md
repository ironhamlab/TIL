- 학습 주제 : 저장 프로시저(Stored Procedure)와 데이터 접근 방식 비교

---

#### [학습 내용]

* 저장 프로시저 vs ORM/JPA의 근본적 차이
  - ORM(JPA/Hibernate)은 Entity를 분석해서 실행 시점에 SQL을 자동 생성하는 방식이고, 저장 프로시저는 SQL 로직을 미리 DB 안에 저장해두고 호출만 하는 방식이다.
  - 결국 둘 다(그리고 MyBatis도) 최종적으로는 JDBC를 거쳐 DB와 통신한다 — JDBC는 대안이 아니라 모든 방식이 공유하는 공통 통로다.

* "SQL을 어떻게 짜고 관리하느냐" 기준 4가지 축
  - 순수 JDBC 직접 코딩, ORM(자동 생성), MyBatis(직접 작성 + 매핑 자동화), 저장 프로시저(DB에 미리 저장) — 이 넷이 실무에서 실제로 논의되는 선택지다.
  - QueryDSL, Spring Data JDBC 등은 이 4개 중 하나를 보완/변형한 곁가지에 가깝다.

* 저장 프로시저의 트레이드오프
  - 장점: 성능(미리 컴파일됨), 네트워크 트래픽 감소, 여러 애플리케이션 간 로직 재사용, 규제 산업(HIPAA, PCI-DSS 등)에서의 보안 이점
  - 단점: 버전 관리(Git) 어려움, 디버깅/테스트 어려움, 특정 DB 벤더 종속, 로직이 코드가 아니라 DB 안에 숨어 가독성 저하

* 업계 동향은 양극화되어 있다
  - 최신 웹/스타트업/마이크로서비스 진영은 ORM 선호로 이동 중
  - 금융, 의료, 정부, 대형 레거시 시스템 등 규제·안정성 중심 조직은 여전히 저장 프로시저를 표준적으로 사용하며, DBA 직무 자체가 이런 문화권에서 존재

#### [느낀 내용]

- "오래된 기술이니 몰라도 된다"고 넘기기보다, 내가 속한 학습·면접 환경이 어떤 기술 문화권에 있는지 먼저 파악하고 그에 맞춰 학습 우선순위를 정해야 한다는 걸 느꼈다.
- 개념을 "이게 정답이다"가 아니라 "어떤 트레이드오프 위에서 특정 상황에 유리한 선택지다"로 이해하니 훨씬 덜 헷갈렸다. ORM이 대세라고 저장 프로시저가 틀린 게 아니라, 조직의 규모·규제·세대에 따라 합리적 선택이 달라지는 것뿐이다.

#### [활용 방안]

- 지금 참여 중인 프로젝트(Todo, PayFor)는 규모상 ORM(JPA)만으로 충분하므로 그대로 진행
- 저장 프로시저를 선호하는 멘토·면접 환경을 고려해, MySQL 기본 프로시저 문법(`CREATE PROCEDURE`, `IN`/`OUT` 파라미터) 정도는 별도로 짧게 학습 목표에 추가
- 새로운 기술 스택을 마주할 때마다 "이 팀/조직이 왜 이 선택을 했는지"부터 먼저 파악하는 습관 들이기
